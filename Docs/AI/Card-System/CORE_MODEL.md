## Purpose and status

This document is the implementation contract for card-related code. It exists so the small Phase 1 test hand can grow into the complete Wasp set, then five additional distinct heroes for the private 3v3 pitch, and eventually an authorized roster of roughly 40 heroes without putting card rules in Unity scenes, UI callbacks, or card-name conditionals.

`CARD_EFFECT_CAPABILITIES.md` is the mandatory effect-level companion. It defines the reusable contracts for Object Push, source-relative direct Move, Place, Spawn, tokens, markers, board-object changes, keyword queries, modifiers, timing, and other card-driven operations.

The current model implements immutable definitions, owned instances, per-hero commitments and Pass, reveal/Initiative, action offers, all current pending choices, complete card lifecycle and retrieval, typed effects and consequences, deterministic replay/Undo, and schema-v34 snapshot restore for the six configured hero sets. Snapshots remain an orthogonal persistence, diagnostics, and future resynchronization boundary rather than per-command Undo entries. New cards extend these definition/instance, offer/context, continuation, command/event, and snapshot seams through verified typed capabilities or explicitly isolated handlers.

The contract is based on the second-printing rulebook's game structure, Action Card anatomy, action execution, card states, Movement, Skill, Hold, Attack, Defense, leveling, items, active effects, and keywords on printed pages 7-19. Exact hero content still requires the source-verification milestones in `ROADMAP.md` and `RULES_LEDGER.md`.

This is an architecture specification, not evidence that any card rule is implemented. Implement only the subset named by the currently approved micro-milestone.

## Rule-driven design pressures

The card system is more than a collection of numeric values:

- A played card offers one Primary action and one or more Secondary actions, but exactly one action is chosen. Hold is generally available even without a printed icon.
- Fast Travel and Clear replace an entire action. Defense is a reaction from a card in hand and is an exception to normal turn action selection.
- Card text applies in some invocation contexts and not others. In particular, printed Primary action text, Secondary actions, replacement actions, and Defense responses cannot be flattened into one generic "use card" operation.
- Actions contain ordered mandatory and optional steps, target choices, modal choices, conditions, repeats, and early termination when a mandatory step cannot be completed.
- Resolution can pause while a player chooses a target, option, distance, card, or whether to use an optional step, then resume without changing the outcome.
- Card states overlap. A resolved card is still played; a rare discarded card may also be played; facedown is an information and rules property that can cancel an active effect.
- Attacks open a Defense response and have explicit before/after timing. Active effects can last for a turn, round, next turn, or another defined window and can be canceled by state changes or defeat.
- Ultimates and token properties can be continuous rules sources rather than ordinary Active effects, with different lifetime and cancellation rules.
- Hold and resolving a card without performing an action are different rules paths even though neither executes printed card text.
- Some systemic consequences happen during or immediately after an action. Defeating/removing the last Battle-Zone minion can Push the lane before a repeated action continues, while displaced minions return to the Battle Zone only after the action.
- Targets can be heroes, minions, units, tokens, spaces, cards, or other rules objects. Range, Radius, adjacency, straight lines, zones, allegiance, immunity, and presence checks are distinct concepts.
- Printed icon values, card-text modifiers, items, minion modifiers, and active effects contribute differently. Items modify matching printed icons, not arbitrary numbers mentioned in text.
- Upgrades replace card definitions while items and Ultimates occupy different rules roles.

These pressures require explicit action context, resumable resolution, orthogonal card state, typed targeting, and deterministic timing from the beginning.

## Non-negotiable invariants

1. Authoritative card rules are plain deterministic C# with no dependency on `GameObject`, `MonoBehaviour`, animation, scene objects, UI state, or wall-clock timing.
2. Static card content and mutable match state are different models. A runtime card instance never mutates its card definition.
3. Rules code never switches on a display name, image filename, or hero name to decide behavior.
4. Printed text is stored for display and source auditing but is never parsed at runtime. Structured definitions are the authority used by the resolver.
5. Every player decision enters through a validated command. Every accepted state change produces ordered rule events.
6. Any resolution that awaits a choice is represented by serializable authoritative data, not a delegate, iterator, Unity coroutine, closure, or UI callback.
7. Action origin and invocation context are explicit, so Primary, Secondary, replacement, reaction, repeated, and card-text-created actions cannot accidentally share the wrong rules.
8. Card state is not forced into one mutually exclusive enum when the rulebook permits multiple simultaneous facts.
9. Common behavior is composed from small typed rule components. A genuinely unique card may use a controlled pure-code handler, but it uses the same validation, choice, event, timing, and serialization boundaries.
10. New content extends the system locally. A normal new card should add definitions and scenario tests; a truly new mechanic should add one isolated typed primitive or handler and its tests, not branches throughout the turn engine, UI, or state model.
11. Card definitions and effect handlers have no generic randomness primitive. The only randomized game input is the separately owned initial Tie Breaker setup result.

## Authoritative conceptual model

Names below are conceptual contracts. Exact C# names may change, but the responsibilities and boundaries must remain.

| Model | Responsibility | Must not contain |
| --- | --- | --- |
| `CardDefinition` | Immutable, versioned rules content shared by every copy of a card | Match ownership, current state, scene references, mutable counters |
| `CardInstance` | Stable runtime identity, owner, definition reference, and current card-state facts | Parsed text, duplicated rules content, presentation state |
| `ActionDefinition` | Immutable structured content for one printed or general-rule action | Runtime actor/source, current availability, UI widgets |
| `ActionOffer` | One currently legal context-bound use derived from an action definition and authoritative state | Duplicated card content, UI widgets, direct state mutation |
| `EffectDefinition` | Structured ordered behavior for an action or active effect | Arbitrary executable strings or scene operations |
| `CapabilityOutcome` | Serializable typed facts from one effect node, available to later nodes and checkpoints | Presentation-only state, untyped dictionaries, hidden callbacks |
| `PendingResolution` | Serializable progress through one action, including prior choices and current timing position | Delegates, coroutines, hidden UI-only choices |
| `PendingChoice` | The exact legal decision currently required, its chooser, candidates/constraints, and continuation location | An already-assumed answer |
| `ActiveEffectInstance` | A live effect's source, controller, scope, trigger, duration, and cancellation conditions | Presentation-only duration or animation state |
| `ContinuousRuleSource` | A persistent rules-property provider such as an Ultimate or token property, with its own applicability lifetime | Accidental Active-effect/card-state cancellation semantics |
| `RuleEvent` | An ordered fact emitted after accepted rules changes for logs and presentation | The authority to decide another rules outcome |

An offer's availability is decided rather than assumed. The card query that builds offers sees card state alone, so every offer it produces claims to be available; the turn authority stamps the answer onto the offer it was handed rather than rebuilding one that could differ. Three rules answer it, each returning true for the others': a Skill whose effect can apply nothing (6.5af), an Attack the rules can prove has no legal target (7.8a1), and a printed primary whose card text has no typed composition yet (8.4). The third reads the action definition's own `PrintedTextComposition`, which names the milestone that owes the composition or the trigger that would schedule it. An action declaring one is drawn as an action that exists and cannot be taken, and every start command naming it is refused atomically with a typed reason before any resolution frame exists - performing it would carry out the printed values and silently drop the printed sentence beside them, which the match cannot detect afterwards. Rulebook p.12 makes refusing costless as well as correct: a hero may Hold rather than act, and the replacements p.13 gives a Movement or an Attack are still offered against a greyed one. The judgement is stated once, so the offer set and the start command cannot disagree, and it is asked of the action rather than of the card, because a card whose primary is owed still prints a complete secondary.

Milestone 8.5 gave `ActionDefinition` its second kind of effect content. A Skill's `EffectRoot` is the action - rulebook p.12: "When you perform a Skill action, simply apply the card text" - so it runs when the action does. A printed Attack's or Defense's root is *card text*, applied at one of p.14's numbered moments, so it declares which: step 1's "Before the attack", step 4's Defense action text, or step 7's "After the attack:" once the target has defended or been removed. Movement, Hold, Fast Travel and Clear still carry none, each being an algorithm rather than effect content. The statement is refused in each way it could be false - a root with no moment, a moment with no root, a moment belonging to the other action kind, and a moment on an action whose source-card text p.13 suppresses, which is the rules consumer the `CardTextApplication` policy had never had.

Every printed Attack also carries a `PrintedAttackTargetPolicy`, because p.13 states an Attack's targeting as a rule about the card rather than about its subtype label: enemy heroes and minions by default, at adjacency for a non-Ranged Attack "even if the card has a radius icon" or within the printed Range for a Ranged one, narrowable to heroes alone where a card's own words say so. The default is what every Attack in this build declares, so nothing about an ordinary one changed; what changed is that a card which narrows it has somewhere to say so as typed content.

**Card text applied inside an Attack cannot pause.** The attack's remaining steps are produced in the same command that began them and no persisted state can hold them while a question stands, so `EffectDefinitionValidator.ValidateCardText` refuses a card-text root containing p.10's `Choose`, a `may` step or a `RepeatAction` - at content load, before a match runs. A Skill is unaffected; pausing its own effect is what the frame exists for. The slice that first transcribes a rider needing a question owns the nesting and the schema move it costs.

### Card definitions

A definition needs stable identity and enough structured metadata to reproduce the printed card without reading its image:

- Stable definition ID and explicit content revision.
- Hero/content-set ID, display name, typed `CardColor`, tier, and Basic/non-Basic/Ultimate classification where applicable.
- Printed Initiative, item icon, and printed action/value icons.
- Ordered action definitions with stable IDs local to the definition.
- Structured conditions, target specifications, values, and effect definitions required by those action definitions.
- Exact transcribed rules text and reminder text for display and audit only.
- Source reference and verification status outside runtime gameplay logic.

`CardColor` is a typed rules-facing characteristic, not a visual style, generic slot, or Red/Blue team identity. Rules queries may combine it with owner/controller, location, lifecycle state, face/information availability, and other verified predicates to derive legal card candidates for choices, costs, conditions, counts, or effects such as a color-restricted discard. Same-color progression constrains upgrade candidates, but each valid next-Tier relationship remains explicit rather than being inferred from color alone. No authority may infer card color from artwork, tint, display name, hero identity, or UI grouping.

Milestone 7.1 implements color, Tier, and Basic classification as one required definition argument with no defaulting overload, so a definition that carries none states that explicitly. The five colors are the rulebook's - p.7 ties the primary action icon to the card's color, and p.15 names Gold and Silver as the Basic pair that "are never upgraded, have no Tier, and are not considered when checking your lowest card Tier" - and the type refuses a Basic card of any other color, refuses a Tier on one, and refuses a non-Basic card without one. Tier stops at IV, because that is p.16's Ultimate and the only value above III the source prints in a match; the Handicap "H" Tier is returned to the box during setup. Each non-Basic card states its next-Tier candidates as stable definition IDs, and a relational validator checks each stated candidate against the whole content set for resolvability, same color, exactly one Tier higher, non-Basic, and p.15's count of two for a Tier I or II card and none for a Tier III - which is what keeps color a constraint on progression rather than a derivation of it. The configured synthetic content deliberately assigns colors that no reading of team identity, display name, hand slot, or printed action icon reproduces.

Milestone 7.2 adds the item icon to that same required profile, and states its presence as exhaustively as p.16 does: "On the bottom of every Tier II and Tier III Action card, there is an Item icon." Both directions are refused - a Tier II or Tier III card without one could be set aside by the upgrade step and then never placed under a matching slot, and a Tier I or Basic card with one claims an icon the page does not print on it - so a Tier I card states the absence at its construction site rather than reaching it by omitting an argument. The icon reuses the printed-value channel vocabulary rather than declaring a parallel one, because p.16 closes its Item Bonus box by naming the affected icons - "only the value of the Initiative, Attack, Defense, Movement, Range, or Radius icons on a card are affected" - which is that vocabulary's exact membership; a second enum would have to be kept in agreement by hand, and the first disagreement would be an item matching an icon no printed value can carry.

A hero dashboard declares the four item slots p.16 tucks items under, as that hero's own content rather than a shared constant. The layout is Attack, Defense, Initiative, and a fourth accepting Range, Movement and Radius together: the page states the first and the third itself, magnifying "the first item slot of his dashboard which has the same icon" and placing an Initiative item "under the third slot of his dashboard", and the user supplied the second and the fourth from the component on 2026-08-19, because the page text states neither and its scan will not resolve the label strip further. **A slot is therefore a distinct thing from an icon, and nothing may derive one from the other by identity.** A dashboard is deliberately not required to accept all six icons: one that accepts five is legal content, and refusing an item for the sixth is the rule below rather than a type error - a total-coverage type would make that refusal unreachable.

An item is authoritative per-hero state recording five things: its owner, the card instance that became it, the dashboard slot it sits under, the icon it supplies, and its 1-based order in that hero's sequence of gained items. The slot and the icon are separate fields because the fourth slot carries three icons, so neither determines the other there and two items under one slot can raise different totals. The slot is recorded rather than re-derived on every read because the page attaches a consequence to which slot an item was actually placed under: "If your item was not clearly visible or if it was not placed in the appropriate item slot, the item has no effect!" The order is recorded for the analogous reason - no rule in the source reads it, and an ordering the state does not hold is one a later build can silently change. Several items may share one slot, which p.16 states outright, so no authority treats a slot as a key; the uniqueness that does hold is the card's, since one card instance becomes at most one item. Placement asks the owner's dashboard which slot accepts the card's printed icon, refuses a card no slot accepts distinguishably from a card printing no icon at all, decides every refusal before anything moves, and routes the card's own Facedown-to-Faceup transition through the shared lifecycle authority rather than performing it itself. Because p.15's upgrade step is not optional, setup validation refuses content in which a hero can reach a Tier II or Tier III card whose icon no slot of theirs accepts, over the closure of that hero's own stated upgrade candidates rather than over every definition in the set.

The Item Bonus is decided in exactly one place, for all six icons alike, and implements the three things p.16's box states. Each item adds one and only one to the matching icon, never a scaled amount, and the match is on the icon the item supplies rather than the slot it sits in. An item whose channel the card prints no icon in adds nothing - the page spells that case out, that "if the card has no Range icon, a +1 Range item would have no effect" - which is why the decision is made against an already-computed printed result rather than against a channel name. And items never raise a number in card text: the condition is evaluated over printed-icon contributions alone, so a channel whose only entry came from card text gains nothing and the card-text contribution itself is untouched. Every item contribution names the card instance that became the item, so a total can say which item raised it rather than merely being larger. Every value total this build computes consumes that one query - Initiative, the Attack Total, the Defense Total, the Movement Total, a Ranged Attack's Range Total, and since milestone 7.2b the Radius Total - each by consulting the item state the match already owns rather than by any second derivation.

Milestone 7.2b adds the printed Radius that last total composes. p.9 states where it lives and what it means: "some primary actions have a Range or Radius icon and a value on the right side of the card", "the value on the Range/Radius icon determines the maximum Range/Radius of your action", and "if the card text mentions Range/Radius, it refers to this value". A card text that says "in Radius" is therefore naming the printed icon rather than carrying a number of its own, which is exactly the distinction p.16 draws when it raises icons and never "values in the card text". A Skill action may print a Radius and no other value - what a Skill does is still its effect - and only a primary action may print one, because that is the action p.9 gives the icon to. The same page settles the subtype: "all other actions are non-ranged, including those with a Radius icon", which a Skill is by construction since only an Attack declares a range classification. Milestone 7.2c then bound the one configured card whose text already claimed a Radius to the icon it now prints: a small capability publishes the composed total as a typed fact, the way the actor's-space capability publishes a coordinate, and the consuming step binds it through the ordinary node-output binding. That is what keeps the page's two readings apart in the definition itself - a card-text number is a literal in the node table, a printed value is a binding - and a card printing no icon publishes nothing rather than a zero. The effect frame carries the match's items so a capability reading its own card's printed icon composes the same bonus every other total does, at all five points a capability can be asked - Skill start, repeated-Skill start, the option-feasibility walk, the choice-answer path, and snapshot restore's candidate re-derivation - because a paused disk re-derived without them would come back a ring smaller than the one the player was offered.

Milestone 7.3 adds p.16's Ultimate as the third card classification, and every part of what it states is that page's rather than a modelling choice. It is "a special Tier IV card", so the Tier set reaches IV and the classification is its own rather than a flavour of non-Basic: the page unlocks it "instead of upgrading a card and gaining an item" and places it beside the dashboard rather than in the hand, so classifying it non-Basic would make it both an answer to the lowest non-Basic Tier and a legal upgrade choice. It prints no Item icon, because that belongs to "every Tier II and Tier III Action card"; no next-Tier candidates, because nothing is above it; no Initiative and no action definition, because it is never played; and no colour, because its printed swatch is none of p.15's five and no rule reads it - a sixth colour member would be a value no rule asks about. What it does state is the permanent ability it supplies, as one typed rules modification with a stable identity, and the definition refuses an Ultimate without one and any other card with one. Its applicability is not per-definition content, because p.16 states one applicability for every Ultimate there is: the ability "is always in effect (as long as your hero is on the board)". The relational validator refuses an Ultimate named as any card's next-Tier candidate, distinguishably from a Basic card so named.

The unlock is recorded by the card's own position and by nothing else. p.16 gives it exactly one destination - "Place it Faceup to the left side of your hero dashboard" - so a card location of its own carries the whole fact, and that is also what makes an unlocked Ultimate distinct from an ordinary hand or deck card without any authority having to say so: the hand a turn commits from, the deck an upgrade searches, and the discard pile retrieval reads all exclude it by asking where the card is. Unlike an item, nothing further is recorded beside it: an item's slot is a placement decision the page attaches a consequence to, and the Ultimate has no such choice, so a second record could only agree with the card or be wrong about it. The transition takes the card from the deck, which is where p.6's setup leaves it, and is refused unless the reading names the card's own owner, the card is an Ultimate this content set supplies, no Ultimate is already unlocked for that hero, and p.16's condition holds - "Once you upgrade all your cards to Tier III", expressed as the lowest non-Basic Tier of the stated reading being III and false when that reading selects no non-Basic card at all, so an emptied hand cannot satisfy it by having fewer cards rather than better ones. The reading's scope is the caller's to state, exactly as it is for the lowest-Tier query itself, and the scope p.16's condition uses is the hand, because p.15 returns every upgraded card to the deck and tucks Tier II cards under the dashboard as items.

Milestone 7.5 adds the purchase that moves all of this, and prices it from p.15's printed Hero Level table as declared content rather than from literals: a level up costs the Level it leaves, which is what the table's row and its own caption both say - "The first level up costs 1 coin. Each following level up costs 1 more coin than the previous one." The Level being left is what is priced rather than the Level reached, because the page states the difference outright: "You cannot skip a level. A level 1 hero needs 3 coins to reach level 3 (1 coin for the first level up, and 2 coins for the second)." The table's Max card Tier row is stated beside the cost and consulted by nothing, because over p.15's own hand - the Basic pair plus three non-Basic cards - always choosing the lowest Tier produces that row exactly; it is a printed consequence of the choice rule rather than a second constraint on it, and stating it is what lets the agreement be asserted rather than assumed. The purchase itself is mandatory whenever the coins are there, and the coins are the ones p.13's Defeat awards, so one ledger answers what a hero can afford. Each purchased level either upgrades a card or unlocks the Ultimate, never both: p.16's "instead of upgrading a card and gaining an item" is an either/or, and the two are separately recorded so a resumed purchase cannot do both. An ordinary purchase is p.15's three sentences in its order - return the chosen card to the deck, take one of the two same-colour next-Tier cards into the hand, set the other aside - and one option states both of that step's decisions at once, naming the card upgraded and the card taken. That is a consequence of where an answer can be recorded rather than a reading of the page: the second decision's options are a function of the first decision's answer, so two sequential pauses would need the first answer kept somewhere between them, and the only somewhere is a second record of where the transition is.

Milestone 8.3 fills the transcribed-text bullet above and adds the two statements verified content needs that synthetic content never did. `CardSourceContent` carries a face's printed words verbatim, or states that the face prints none, and it is coupled to `CardContentAuthority` in both directions: verified official content must state one of the two, and a synthetic fixture may state neither, because a fixture carrying printed words would be inventing source authority. It is inert by rule as well as by intent - a conformance check fails the build if any production type reads it back - so the project has a home for card text without having a printed-text parser. `PrintedTextComposition` is the second statement: a printed primary whose text has no typed composition yet names the milestone that owes one, or the named trigger a deferral waits on, so an action that performs none of its printed text is distinguishable from one that prints none. Two shape rules widen with the first verified faces that need them: p.9's sentence "some primary actions have a Range or Radius icon" now admits either icon on an Attack or a Skill rather than Radius alone, and `PrintedDefenseResolution` separates p.14's two Defense shapes, so a Block card declares a Block instead of printing a Defense number - never a sentinel amount, and never an absence that a malformed definition would also produce. An Ultimate likewise carries the p.9 icon its ability reads, which is what lets p.16's item bonus reach it.

The runtime format may later be authored through JSON, ScriptableObjects, or another content tool, but authoring objects must compile into validated immutable rules definitions. A ScriptableObject must never become live authoritative match state.

### Card instances and state

Every physical card in a match has a stable instance ID, a definition ID/revision, an owner, and an explicit current controller when rules require that distinction. Runtime state should represent at least these orthogonal concerns rather than one catch-all state value:

- Physical/logical location, such as hand, turn area/dashboard, discard pile, deck/set-aside area, or item slot.
- Whether the card has been played.
- Resolution status when applicable: unresolved or resolved.
- Face orientation and whether rules-facing information is currently available.
- Any source links needed by an active effect or pending resolution.

Legal combinations and transitions are validated centrally. For example, resolved implies played, but played and discarded may coexist in the rare rulebook case. When a resolved or discarded card becomes facedown, its type, color, and actions are unavailable to relevant rules queries; applicable active effects are canceled. A newly played unresolved card's facedown orientation is handled by the separate hidden play/reveal flow rather than this resolved/discarded suppression rule. Swapping cards transfers the rules states specified by the rulebook rather than merely exchanging two container indexes.

An initial in-hand card may become played/unresolved in the turn area Facedown, reveal Faceup, and become resolved after its action; Defense discard remains a Hand-to-Discard transition. `MatchParticipants` retains distinct `PlayerId` controller/seat and `HeroId` entity identities while enforcing exactly one hero per player. Every configured hero's controller commits exactly one owned card from a nonempty valid hand, only an empty hand permits Pass, and joint reveal waits for all responses. Each assignment carries `HeroId` plus one committed card ID or explicit Pass; controller and team derive through participants. Named staged fixtures may supply two assignments, while the default official configuration supplies six through the same snapshot shape. Retrieval, new-round start, and resolve-without-action are distinct implemented transitions.

State changes such as play, reveal, resolve, discard, retrieve, swap, set aside, equip as an item, and become facedown are explicit rules transitions. UI code cannot assign these properties directly.

## Contract implementation status

This section is the one place that distinguishes a contract this document specifies from a contract the code actually has. This document is an architecture specification, so naming an unbuilt contract is legitimate; leaving a reader unable to tell which is which is not. The living-document validator fails when a named contract carrying one of its known suffixes - `Definition`, `Resolution`, `Event`, `Authority`, `Backend`, `Projection`, `Instance`, `Registry`, `Serializer`, `Query`, `Handler` - is neither declared under `Assets/` nor listed here. Capability names outside those suffixes are specification vocabulary the check cannot reach; the shards mark their implementation status themselves, as the timing shard's status section does.

Remove a row when its type is implemented. Do not add a row to silence the validator for a contract that was supposed to exist.
