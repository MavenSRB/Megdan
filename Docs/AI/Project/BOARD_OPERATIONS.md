## Components on the board

Tokens and markers are authoritative components with stable instance identity and a finite supply, both taken from a trusted immutable catalog that owns supply size, display name, token properties, and marker return condition. A placed token is a board occupant: it joins the shared occupancy index by declaring a typed occupant, so it blocks movement, adjacent moves, and every other occupancy consumer without any of them learning that tokens exist, and no per-kind collision block or commit scan was added. Its trusted definition supplies immutable property declarations; the placed instance derives stable `TokenProperty` continuous sources that remain while that token is placed, never enter `ActiveEffectLifecycle`, and do not end when its source card resolves or the placing hero leaves the board. A marker is an attachment with an owner, a holder, a source, and an explicit return condition, and carries no coordinate at all. Its instance identity is minted through the shared `MarkerInstanceIdentity` contract - source card, action, node, round, and turn composed with the holder - so a card that gives, returns, and gives again produces two attachments that can be told apart rather than one identity used twice, while re-executing a give inside its own resolution stays a legal no-op. What remains in either supply is derived from the catalog total minus what is placed or held rather than stored, so the two can never disagree. Placement, the rulebook's short-supply reclamation, marker give, and marker return execute as registered effect capabilities on the milestone 6.2a frame; every decision inside them rides the existing `AnswerEffectChoice` command, and no token-specific pending-choice class, projection property, or continuation arm exists.

## Displacement

Direct Move and Object Push are two registered capabilities over one shared displacement seam. The board exposes a named displacement port beside its token-placement port, so a capability asks for a validated relocation rather than reaching the whole board authority; the port identifies its subject by the space it stands on, which one-obstacle-per-space makes unambiguous for heroes, minions, and tokens at once, and relocates any of the three without emitting a movement fact, because neither operation is a Movement action. Direct Move relocates whatever stands on the space its definition names, derives its destinations from the same reachability the Movement action uses, and filters by the closer-space query when its text moves a unit toward the source; it cannot become Fast Travel, and a prevented Movement action does not prevent it. How much of a declared distance is optional is one statement of pages 10 and 11 that both displacements read and a conformance rule holds them to, so `up to X` admits the mover's own space - an applied result that relocates nothing and publishes the unchanged space - exactly as an `up to` push admits distance zero, while every other wording still means the exact number of spaces or p.10's stop. Object Push resolves the straight line directly away from the pushing unit, moves each target as far as it can including zero, and asks transit and endpoint separately so a target permitted to cross obstacles must still land on an empty space; an `up to` push chooses one distance, resolves every target against one pre-effect state, and commits them as one batch, working outwards so the batch never refuses itself. Declared immunity filters the push target set while a presence question still counts the immune unit, and a pushed token is asked no immunity question at all. Neither operation records a Lane-Push request. Since milestone 6.5a that Push carries two declarations over one implementation - the adjacency-derived batch above and a target-named form the definition supplies a coordinate to - which differ only in how the target set is produced. The adjacency-derived batch stays behind the synthetic Skill card; direct Move and the target-named Push each reach a player through one configured card. Each displacement is recorded as a typed fact naming the subject, its origin, its destination, and how far short of its request it fell, which is the seam that correction attaches to.

## Clear

Clear is an immediate value-free general replacement offered only for a current replaceable Attack. One `PerformClear` command carries a canonical unique token-identity subset, and Core revalidates the source offer, actor presence, adjacency, and whole selection before removing anything. Empty selection is legal. Accepted resolution removes exactly the chosen stable instances in canonical board order, emits Clear-specific start/removal/completion facts between Action Started/Ended checkpoints, suppresses all replaced Attack text and facts, resolves the source card, and follows the ordinary Initiative, snapshot, replay, Undo, and rule-event-log paths. End-of-round and defeat cleanup triggers remain later Phase 6 work; presentation still has no component or Clear-specific surface.

## Place and Spawn

Place is one shared operation every caller declares against, and Spawn is a separate one because p.18 defines it by ruling out half of Place. A Place states its source container, eligible piece kind, destination query, chooser, and no-destination policy as one immutable policy object that cannot be constructed with any of them missing; its destination query answers an inclusive rulebook-distance disk excluding the piece's own space, or the equally-nearest empty spaces of a declared coordinate set, never a route, because placing is not movement. The operation re-derives its admitted destinations when the answer arrives, relocates a board piece through the neutral fact-free relocation commit or puts a supply token down through the token port, and reports a typed outcome with no movement vocabulary and no origin at all for a supply piece. Three callers share it: the general Place capability, which takes any game piece named by a coordinate and reads its no-destination arm from the node's own failure policy; the token placement capability, whose adjacent-empty-space bound is now that same declared radius-1 question; and the correction fallback, which declares minion miniatures, the nearest empty Battle-Zone spaces, and the owning team. Spawn draws from a named unit-supply port: the declared miniatures not currently standing, derived from a reserve the board holds beside its occupancy, filled by removals and rebuilt on restore as the configured roster minus the restored positions, so no supply count is persisted. A Spawn offers the acting team's supply as its one decision, puts the miniature onto its own configured Spawn point, and removes a covering token inside that same commit while any other obstacle refuses it; no Respawn eligibility or timing rule is implemented. A small actor's-space capability publishes the acting hero's coordinate as a fact rather than a one-option prompt, which is how a definition names the actor as a Place subject at all: roles resolve without board access. One configured card exposes Push and Place to a player - Red Needle's Skill chooses another adjacent unit and Pushes it 3, or Places the acting hero within Radius 4 - and it is the first value-shaped effect choice the ordinary hand reaches, so the scene's coordinate-addressed submitter has a consumer. A second exposes direct Move and Spawn: Red Bombard's Skill directly Moves another adjacent unit up to 2 spaces, or Spawns one supply miniature onto its own Spawn point. No configured card offers both Place and Spawn, and neither branch can reach the other's source container.

## Swap, Replace, and Remove

Three more registered capabilities over a fifth named board port, which exists because none of them can reach the displacement commit: that commit needs an empty destination, and a Swap has two occupied spaces, a Replace never empties the one it works in, and a Remove has no board destination at all. Each states its own declaration and its own typed outcome, and no outcome carries another's vocabulary. Swap reads both objects' positions from one pre-effect state, asks declared immunity about both because the exchange affects each as much as the other, and commits one exchange in which the occupancy index is never momentarily short an occupant; it publishes each object's new space and no route, distance, movement, or placement fact. Replace states where its substitute comes from, where the replaced object goes, whether properties transfer, and which triggers observe it, and refuses to exist without any of the four; the implemented declaration takes a token from a supply, returns the replaced token to its own, transfers nothing, and is one observable replacement, so a policy promising two observable stages is refused rather than quietly satisfied by the single-stage commit. Because a token's properties belong to the instance, substituting a Hazard for a Ward ends the Hazard's continuous source rather than handing it over. Remove declares its eligible piece kind and its destination, runs the removal in named stages, and reports either that the piece left the board or that the removal was attempted and prevented; it awards nothing and opens no Defeat stage, and no declared kind admits a hero, because a hero leaves the board through Defeat and its consequences. The one prevention the engine can currently reach is declared immunity asked immediately before the mutation, so a target legal when a choice opened and immune when the answer arrives stays where it is; the general prevent-removal source family stays unimplemented for want of verified card text. That named stage is shared rather than the Remove's own: the Attack's Defeat asks it the same first question before taking its target off the board, so a minion the rules protect cannot survive one path and die to the other, and a prevention source added later is honoured by both or by neither. Each caller declares which of the two it is, because nothing about an emptied zone distinguishes a Defeat from a removal and only the operation that ran knows.

Only a completed removal asks whether a Lane Push is owed, and that is a structural property rather than a tested sample: the question lives in one query, the removal stage is its only caller, and a conformance rule holds it that way, so moving, pushing, or swapping the last Battle-Zone minion cannot acquire the cause by being written later. The question counts the same effective Battle-Zone minions the Minion Battle counts, from one shared derivation, and the recorded cause names which of the page's two sentences it answers, the side left with none, and the zone it emptied. Both sentences now have a producer: a standalone Remove records the removal cause and the Attack's Defeat records the Defeat cause, each through that one shared stage. It is a cause and never a request; emitting and resolving the mid-turn push belongs to a later milestone. All three operations are reached only through the synthetic Skill card, and each names the piece it works on by a space published by an earlier selection node; the after-action displaced-minion correction runs after them exactly as it runs after every other Skill, so a Swap that strands an intrinsic minion outside the Battle Zone returns it without declaring a correction of its own.
