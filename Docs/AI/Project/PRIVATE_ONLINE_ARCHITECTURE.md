## Decision

The lobby's [host-owned bot contract](PRIVATE_SESSION_BOTS.md) preserves these session boundaries without child player processes.

For the private Windows playtest track, use one dedicated seatless authoritative host process connected to six clients over direct TCP sockets:

- Unity Editor **6000.5.9f1** and URP **17.5.0** remain the project baseline. No networking package is installed; `Packages/manifest.json` and `packages-lock.json` are untouched by this track.
- The byte transport is `System.Net.Sockets` TCP inside one project-local, Unity-free adapter assembly beneath the transport-neutral session port. No relay, no third-party service, no cloud account, and no service credential exists anywhere in the stack.
- The host binds a configured address and port, loopback by default; clients address it by IP and port. A reachable address is operator-supplied - one machine today, an operator-run Windows server later.
- Invite-only admission is carried by an optional pre-shared session key: the host issues a random challenge and a client must answer with proof of the same key. The key also seals the link. **Milestone 8.32 resolved the encryption decision this record owed** with a project-local pre-shared-key AEAD frame layer instead of `SslStream`: per-connection, per-direction keys are derived with HKDF-SHA256 from the session key and that connection's random challenge nonce, each frame is encrypted with AES-256-CTR keyed by its own strictly monotonic sequence and authenticated encrypt-then-MAC with HMAC-SHA256, and after a verified key proof every frame travels sealed in both directions except host-to-client terminal Reject/Goodbye messages, which carry no secret. A keyed client's Goodbye is sealed: it forfeits a seat and its reconnect capability, unlike a socket reset. `SslStream` was rejected because a certificate would have to be generated, distributed and pinned beside a key that already exists, and a stream-level handshake sits badly beneath the bounded frame assembler and the single-threaded pump. An unkeyed session has no key to derive from, stays plaintext, and may bind only the loopback interface - every host surface refuses a non-loopback bind without a key, from one shared rule since milestone 8.35a1 - so an owner-private byte can cross plaintext only where this record's on-path observer does not exist.
- Client identity is one opaque connection-scoped ordinal assigned by the host; there is no account, no durable identity, and no authentication service. A returning player is recognized only by the owner-private reconnect capability issued with that seat's grant; the host rotates the connection epoch and never treats a fresh ordinal as identity or transfers the seat.
- Protocol family is `guards-private-online`, current protocol version **12**; version 1 was the initial admission/session wire and version 2 the complete gameplay wire through milestone 8.35b. The family remains independent of socket internals. The application protocol serializes bounded data-transfer objects rather than CLR/Unity objects or `MatchSessionProjection`.
- The host is one serialized executor around the existing Unity-free `IMatchSession`, holds no seat, and plays no hero; all six players are clients. Host loss is terminal for the current match. There is no authority migration.

Milestone 8.31 owns the socket adapter assembly and its conformance boundary; an unexpected engine, assembly, or protocol change blocks that milestone.

## Why this is the minimum supportable choice

**8.36b compatibility assessment:** protocol 12 requires sealed client-to-host Goodbye after keyed admission. Protocol 11 and earlier peers are rejected before payload interpretation; no downgrade or migration. Host terminal messages and pre-admission rejection remain non-forfeiting signals. Frame payload layouts, snapshot schema v40 and all rules/content identities stay unchanged. A forged/tampered departure closes only its connection while retaining the seat reservation and reconnect capability; authenticated deliberate leave still forfeits it.

Authoritative gameplay is already a synchronous, deterministic, Unity-free session that needs ordered command/projection messages, not replicated scene objects, prediction, rollback netcode, or distributed ownership. Direct TCP supplies exactly ordered bounded byte delivery with nothing else attached: no third-party service, account, credential, quota, free-tier limit, outage window, data-processing agreement, or retention policy. The whole stack is project-local and inspectable, no external terms govern it beyond the Unity engine license the project already carries, and deleting the adapter assembly removes it entirely.

The costs are equally plain. The operator must supply a reachable address and port: on one machine that is loopback, and for internet play it is an operator-run Windows server with a public address, which is what replaces the relay's NAT traversal - the tester-side connectivity burden the 2026-08-28 evaluation weighed moves to the operator, and the rented host is exactly what pays for it. Peers learn the host's address and the host's operating system sees client addresses; the mitigation is that no remote endpoint is ever logged, projected, or forwarded, and connections are identified everywhere by opaque ordinals. The link was plaintext while milestone 8.31 carried only handshake and seat-claim bytes; milestone 8.32 put owner-private projections on the wire and paid the owed prerequisite in the same slice - a keyed session is sealed from the key proof on, and a session without a key is confined to loopback. A reachable port also means anyone who can reach it can attempt admission; the pre-shared session key is the admission control that keeps the session invite-only.

## Authority, ownership, and wire boundary

The host process is trusted for rules resolution, seat assignment, ordered execution, version publication, snapshots, and recovery. Nothing else is trusted: there is no service tier, and every client, every received byte sequence, and every gameplay claim inside it are untrusted.

At admission, the host binds one live transport connection, identified by an opaque host-assigned connection ordinal, to one immutable `OnlineSeatId`. Before the match starts, that seat is assigned exactly one existing `PlayerId`, hero, and team through the authoritative participant graph. The binding is host state outside `DirectorCommand`; payload `HeroId`, `PlayerId`, `TeamSide`, seat, or chooser fields never establish caller identity. Reconnect may replace the connection under the session-held reconnect capability milestone 8.34 defines, but never transfers a seat. The host address is a locator and the session key is an invitation gate; neither is authorization to control a seat.

There are three information classes:

- Public: map, units, lives, wave/round/turn state, revealed cards/commitments, public events, connection/ready state without service identifiers.
- Team-shared: only state whose rules or an approved team-owned choice makes it visible to that team.
- Owner-private: the seat's never-public hand cards, unrevealed commitment identity, owner-only offered commands, and reconnect capability. It is absent from every other seat's serialized projection. A card whose identity entered the bounded public match log remains public knowledge if it later returns to that owner's hand; only that structurally public identity is retained, never an otherwise hidden hand or deck card.

The full director projection, accepted-command history, Undo/restart controls, snapshots, diagnostic bundle, host bind/remote addresses, session-key material, and host-only fault detail are never client projection fields. The host may keep privacy-reviewed local diagnostics. Client diagnostics permit protocol/build/schema/map/content/format identity, opaque run/capture IDs, own seat/submission ID, projection version, public terminal outcome, message kind/size, bounded rejection code, and recovery transition. No private hand, payload, endpoint, key or retained capability belongs in collected evidence.

## Protocol and compatibility contract

Every application message has a bounded header: protocol family/version, session ID, message kind, payload length, sender connection epoch, monotonic per-direction sequence, and correlation ID. Milestone 8.31's session frames carry that envelope's first slice - magic, protocol version, message kind, and a validated length - and milestone 8.32's gameplay messages carry the remainder: the session correlation published at admission, the sender's connection epoch (initially 1 and rotated on reconnect), a strictly monotonic per-direction gameplay sequence, and correlation. The initiating seat's result and follow-up complete projection echo its submission or recovery correlation; observer/public pushes carry zero, so an unrelated projection cannot release that seat's in-flight input wait. A wrong session, epoch, or sequence value is a protocol refusal that closes the connection before any seat-level answer. Client submissions additionally carry a random unique submission ID and expected owner-projection version, both outside the gameplay payload. The gameplay payload is one discriminated, bounded command DTO mapped by the host to an offered typed command; it is never an arbitrary serialized `DirectorCommand` object graph.

Admission succeeds only when these values match the host: protocol `guards-private-online/12`, build identity, snapshot schema **41**, map `official-single-lane` plus its current pinned revision, and every registered content revision/digest. The tuple is captured once at host construction and never recomputed, which is load-bearing rather than incidental: a reconnecting client recomputes its own from a local composition that knows nothing of the lobby's hero picks, so an identity republished from a chosen line-up would refuse every reconnect at a format where the chosen set genuinely differs. The host also publishes the immutable six-seat roster and assignments. A mismatch is rejected before private projection or gameplay bytes are sent. Unknown message kinds, discriminators, fields whose forward handling is not explicitly declared, or unsupported schema/content revisions reject; they do not downgrade, rebind, or best-effort deserialize.

The host is the sole authoritative gameplay-version allocator. Each accepted command increments that version once, then produces one owner-scoped projection per connected seat from the same committed state. Public agreement statements and recovery may republish a complete projection without moving gameplay version, so each client also counts accepted projection receipts monotonically for presentation invalidation only; that receipt revision is never authority or a wire claim. A client may display only its latest complete projection. Deltas are optional later optimization; protocol 4 correctness uses complete bounded projections. A reconnect/resync sends a fresh complete projection after compatibility and seat reauthorization, never a client snapshot, and the reconnecting HUD stays non-actionable between the seat grant and that projection.


**Milestone 8.35z60 compatibility assessment.** The seat projection gains one field: rulebook p.8's shared Wave-counter pool as it currently stands, a plain `Int32` beside the per-team Life counters it is the table-wide counterpart of. Carried rather than derived, because a seat holds no rule material saying how many pushes a match has spent, so a client-side count would re-read the host's rules; not optional, because the host always knows it. No new message kind or refusal code. Incompatible: the protocol advances to **11**, no migration is approved, and versions 1-10 are rejected from the bounded header before either peer interprets a payload - a version 10 reader would take the new integer as the hero-row count following it and mis-decode the rest of the frame, structural drift rather than a dropped tail. **Schema stays v40**: the Wave total has been an ordinary counted value in the snapshot's round section for far longer, so what moved is which number a remote read model reports, not what a payload contains. No privacy surface moves - the pool is public at a real table and already unscoped in every in-process projection.

Compatibility assessments for superseded wire versions are completion evidence, so they live in their own milestone commit bodies indexed by [../Archive/Phase-Handoffs/PHASE_8.md](../Archive/Phase-Handoffs/PHASE_8.md): protocol 2 in milestone 8.35b (`03e5b57d`), protocol 3 in milestone 8.35f (`c3763ef5`), protocol 6 in milestone 8.35r (`76bff78f`), protocol 8 in milestone 8.35z14 (`48f92c28`), protocol 9 in milestone 8.35z16 (`26e27e89`), and protocol 10 in milestone 8.35z37 (`02c6c841`), routed out here by this same rule as each was superseded. This record states the current contract, not the history of superseded ones. The protocol 9 entry is recorded late: that assessment was never written here, so this record claimed protocol 8 as current while the build shipped 9, and the correction is noted rather than backfilled silently.

Upgrade rule: any editor, adapter-assembly, socket-usage, protocol, serializer, schema/map/content identity, authority, or build-target change requires a written compatibility assessment. If wire meaning changes, increment the protocol version and reject the prior version unless an explicit migration is approved and tested. Re-run the Win64 build smoke for adapter/build changes, protocol fault/compatibility tests for wire changes, projection/privacy and replay/restore checks for authority/serialization changes, and the full 8.36 gate before using a changed stack for invited testing.

Removal path: all socket types remain in the Unity-free adapter assembly beneath a transport-neutral application protocol port. Removing the transport deletes that assembly while retaining local seat/session, projection, authorization, codec, fault, and deterministic host tests. A replacement transport must reproduce connection context and ordered bounded byte delivery; it cannot enter Core or become rules authority.

## Failure and disconnect policy

### Attributable local captures (8.36d)

Production hosts obtain a fresh injected nonce at construction. `SessionCorrelation` combines the stable compatibility digest with a 128-bit hashed instance suffix; Welcome, envelopes and retained reconnect capabilities use that same opaque value for the host's lifetime. `PrivateSessionIdentity.Correlation` remains the compatibility digest, not a run ID. Deterministic in-memory fixtures may inject fixed entropy or omit it; the evidence writer refuses the legacy non-instance form. Protocol 12 and the schema version established by the current compatibility identity remain unchanged by attributable captures: existing bounded string fields already carry the host-issued opaque identity, with no new wire layout or game-state meaning.

Ordinary lobby processes write public-metadata-only captures to `Logs/online-runs/<run>/<capture>.log` (Editor: `tmp/online-runs`). A completed host declares human/bot seats; each human client declares its own terminal version, cause and winner. Leaving before completion records an abort. Play/Host launchers retain general logs in distinct `Logs/launches/<capture>` directories; rehearsal invocations similarly get unique directories under `tmp/private-online-runs`. These general logs are not the sanitized bundle.

`Tools/Validate-PrivateOnlineEvidence.ps1 -LogPaths <paths> -OutputDirectory <new-directory>` rejects mixed identities, incomplete/duplicate participants, incompatible terminal declarations and unexpected fields. It copies only accepted captures into a new directory and records SHA256 hashes and identities in `manifest.json`. Omit OutputDirectory for read-only validation. This binds local evidence, not an external-network or human-play claim; nothing uploads. The accepted old-build 8.36 session is not retroactively recaptured.

### Bounded TCP service (8.36c)

The listener retains at most twelve connection slots before application admission; a closed slot is not reused until its final event is consumed and both socket workers have exited. Each slot owns one reader and one ordered writer, plus one shared accept thread. Each peer can retain at most 64 incoming frames and 512 KiB of incoming payload; control events are limited by the retained slots (Connected, optional stream rejection, Disconnected). The frame assembler's existing 64 KiB payload limit still applies. One transient accepted socket can be rejected before it receives a slot or worker.

Outgoing frames are copied into an ordered queue, capped at 64 queued frames and 1 MiB including the writer's in-flight bytes. Socket writes occur only on that writer, with a one-second send timeout. Queue overflow or I/O failure closes only the connection; the host receives ordinary disconnect and preserves its seat reservation/pause. Closing never needs a lock held across socket I/O. Normal Close drains already queued terminal messages; Dispose allows one shared 200 ms drain window, aborts remaining sockets, and joins all owned threads within one shared 750 ms budget, reporting failure if a worker remains alive.

Both ordinary-lobby and standalone host/client pumps use the transport's finite Drain batch of at most 64 events per update, leaving time for sweeps, control and UI work. Limits bound local adapter resources, not internet latency or a production denial-of-service guarantee. Wire protocol remains 12; the resource bounds do not alter snapshot schema, framing, payload interpretation, authorization or game-state semantics. Closing checks are owned by [8.36c](../Roadmap/PHASE_8_PRIVATE_GAME_CORRECTIONS.md).

All input is length-checked before allocation-heavy decode and semantically validated before mutation. One malformed input rejects that submission; repeated malformed/oversized or protocol-invalid input disconnects that client. No rejection advances state or projection version.

| Condition | Required result |
| --- | --- |
| Duplicate or replayed submission ID | Return the cached result for an identical already-completed submission when retained; otherwise reject `DuplicateSubmission`. Never execute twice. |
| Stale expected projection version | Reject `StaleProjection`, send no mutation, and offer one bounded current-projection resync. |
| Future version or out-of-order client sequence | Buffer nothing for gameplay; reject and require resync. Reliable transport ordering is not authorization. |
| Malformed, unknown, or oversized message | Reject before session mutation; disconnect on protocol violation or repetition. |
| Command not in the seat's current offered surface | Reject `UnauthorizedCommand` even if it is otherwise rules-legal. |
| Payload identity conflicts with trusted seat ownership | Reject `OwnershipMismatch`, record privacy-safe host diagnostic, and disconnect on repeated attempts. |
| Service/session/build/schema/map/content/protocol mismatch | Refuse lobby admission or reconnect before any private projection. |
| Connection lost before a seat is claimed | Close silently; no seat state exists to preserve and no reservation is created. |
| Client disconnect outside a pending choice | Keep the seat reserved and pause new authoritative progress until reconnect or host termination; no AI/substitute takes control. Only that seat's owner-private reconnect capability may reclaim it. |
| Client leaves deliberately (`Goodbye`) | Release the seat to `Open` and clear its capability: the leaver chose the exposure, and the seat is claimable again by an ordinary keyed claim. Recorded as a release rather than a reservation, because the two mean opposite things to a returning player. |
| Client process exits or crashes, then relaunches | The seat is reserved as for any dropped link. The returning process presents the capability its own machine retained for that seat, scoped to one session correlation and dropped when that session ends; it is armed only against a seat the roster reports `Reserved`, so a leftover entry never turns an ordinary join into a refused reclaim. The capability is at rest on the returning player's machine only, never on the host and never in a log. |
| A reserved seat whose player cannot return | The host may release it by a deliberate manual act, and only so: never automatically and never on a timer. This is the one road back that proves nothing about who is taking the seat, and an auto-release would hand a dropped player's seat to whoever reconnected first. A claimed seat is refused - a live player is never displaced. |
| Client disconnect while it owns any of the ten pending-decision families | Preserve the exact pending family and ordered answers, pause, then reproject it after authorized reconnect. No default answer or timeout mutation. |
| Disconnect during team-owned choice | Preserve the authoritative designated chooser/team contract; no other seat inherits control unless existing rules authority explicitly offers that answer to it. |
| Reconnect within the live host session | Present the reserved seat's owner-private reconnect capability, rotate connection epoch, discard old connection input, send a full compatible owner projection, then resume. A seat grant alone keeps input disabled until that projection arrives; a failed dial restores retry eligibility without discarding the capability. |
| Host disconnect/process loss/listener loss | Terminal `HostLost`; clients clear actionable UI. No host migration, partial restore, or continuation claim. A new match may be created explicitly. |
| Host unreachable before play (wrong address, closed port, refused connection) | Bounded join/host failure with retry; director/local modes remain usable and no private match is claimed. |

The ten current pending families each have deterministic disconnect-before-answer, disconnect-after-send-before-response, duplicate-after-reconnect, stale-answer-after-resync, and successful-reconnect cases, delivered by milestone 8.34 as `PendingDecisionReconnectTests`. The host retains one bounded idempotency window sufficient for reconnect/retry and rejects submissions older than it; 8.33 chose its exact size from measured retry traffic - worst per-seat distance 27 across the deterministic walk - and recorded it as `PrivateSessionProtocol.SubmissionIdempotencyWindowEntries` = 256 under that measurement's own growth check.

## Lightweight threat model and limitations

Protected assets are authoritative match integrity, per-seat control, owner-private/team information, compatibility, and useful privacy-safe diagnostics. Relevant adversarial or faulty actions are forged seat/hero claims, a guessed or shared session key, unsolicited connections to a reachable port, captured/replayed submissions, stale clients, malformed/oversized payloads, message delay/reordering/duplication, abusive reconnects, private-data logging, an on-path observer of the plaintext link, and a modified client inspecting every byte it receives.

Controls are structural owner projections, host-side seat binding, offer-surface admission plus final rules validation, protocol/version pins, bounded codecs on a loopback-default listener, the pre-shared session-key challenge, the sealed frame layer on every keyed session, sequence/version/idempotency checks, opaque correlations, log allow-listing, and terminal host-loss behavior. Tests deliberately violate each control. An unkeyed session is loopback-only. The pre-proof handshake and host rejection/close notices remain readable; client deliberate Goodbye in a keyed session must authenticate. A forged plaintext departure can disconnect but cannot forfeit its reserved seat. The session key's strength is the seal's strength - a guessed key reads the session - which is accepted for invited trusted testers holding an operator-issued key.

The host is operator-run rather than player-run, so no player process holds rules authority - a strictly stronger boundary than the listen host this amendment replaced. The operator can still tamper with the host process, inspect all authoritative state, refuse or fabricate delivery, or alter a locally built binary; client authorization does not make the authority cheat-proof against its own operator. This is accepted only for six invited trusted testers and must be stated in playtest instructions. Production competitive security, anti-cheat, secure secret storage, DDoS guarantees, moderation, accounts, and malicious-host detection are out of scope and require a separate production reassessment.
