## Core architecture constraints

### Map progression

- Phases 1 through 3 use an expanded temporary test grid only for foundational movement, obstacles, cards, two-hero combat, Initiative, turns, and rounds.
- Phase 4 replaces that grid in the main validation scene with the complete official multi-zone single-lane map.
- The full map model includes every official space, terrain classification, zone, zone boundary, zone adjacency, spawn point, Throne, starting Battle Zone, and ordered lane relationship.
- Map content is selected once per match by stable `MapId` plus content revision. `SpaceId`, `ZoneId`, and `SpawnPointId` are map-local; persisted, catalog, external, or cross-map references compose `MapId` with the applicable child ID. Internal coordinate-based rules and queries may remain local to the match's selected immutable map definition, while loaders, snapshots, and presentation must carry or derive that selection and must not assume one static map or make a bare coordinate globally unique.
- Fast Travel cannot begin until same-zone, adjacent-zone, and non-adjacent-zone queries are verified on the full map.
- Lane pushing cannot begin until the full ordered lane, movable Battle Zone, Thrones, and per-zone minion spawn points are verified.
- Do not use a reduced or invented map as evidence that Fast Travel or lane pushing is correct.

### Authoritative state

- Rules state is plain, deterministic game data, not Unity scene state.
- Logical hexes use integer axial `(q, r)` coordinates; generic adjacency is the six standard axial offsets exposed as named directions.
- The model uses collections and stable IDs for teams, players, heroes, cards, units, spaces, zones, and effects.
- Executable setup configuration declares its required immutable `MapId` plus content revision. Every configured external space/spawn reference composes that `MapId` with the map-local child ID, and setup authority resolves all placements only against the exact selected definition before exposing immutable team resources and unit state.
- The default official six-player Quick Game and named staged fixtures share stable unit identity, team, type, spawn, occupied-space, and coordinate data; obstacle, Defense, battle, removal, respawn, and Lane behavior all use that one representation.
- The model must support exactly three independently owned heroes per team for the pitch without hard-coding that team size into general rule APIs.
- Authoritative state must be serializable and schema-versioned.

### Commands and events

- The UI submits commands such as play card, choose action, select target, or confirm movement.
- A rules authority validates commands and produces ordered state-change events.
- Multi-step actions pause on authoritative, data-shaped pending choices and resume through follow-up commands; UI callbacks never own the continuation.
- For the ten declared genuine pending-decision families, each immutable application projection derives at construction at most one `PendingDecisionContract`: a stable semantic family identity and the exact ordered `DirectorCommand` objects implied by the existing typed pending object and invocations. Companion resolution envelopes, commitments, ordinary actions, Hold, Fast Travel, Clear, and end-of-round advance remain outside it. The contract is derived state rather than a snapshot field, and its commands are answer tokens rather than pre-authorization; command authority revalidates every submission.
- Calling a newly introduced or widened reusable foundation general is a test-governance claim, not runtime authority. The test-owned shared-foundation catalog resolves each claimed production owner and exact evidence locator mechanically, distinguishes materially independent shapes from differently named equivalents, and permits a unique capability to remain explicitly narrow with a stated scope and expansion trigger. A later hero-batch capability/foundation delta must reconcile with that catalog before scheduling; the catalog does not register runtime behavior or claim whole-repository generality.
- Director-mode authority runs locally in-process.
- Private online authority runs in one host/session process behind the same typed command, ordered-event, pending-choice, and versioned-snapshot contracts; clients never own rules resolution.
- Randomness must not be generalized beyond the initial Tie Breaker setup decision, and since milestone 8.28b it enters through exactly one seam: `SetupRandomnessAuthority.DrawSeed` records a seed in authoritative setup state, and every decision that needs a draw derives from it by named purpose. Nothing else in the authoritative assemblies may reach platform entropy, which `SetupRandomnessConformanceTests` holds mechanically rather than by convention. The seed rides setup state rather than the snapshot payload, because setup is supplied to a restore rather than read from it; the resulting side is what the payload carries, since it flips during play and the draw does not.

### Application service and presentation

- The configured match uses one pure C# `GuardsDigital.Application` match-session port as its live/replay orchestration boundary for director presentation and future transports. It owns the current authoritative match composition but does not absorb or duplicate domain rules. No unconfigured presentation drill exists alongside it: milestone 6.1c deleted the last one.
- The small composition root creates one bounded non-`MonoBehaviour` session runtime, wires the five peer feature presenters and passive views, configures passive board-view callbacks for hero and destination pointer intent, and gives GUI drawing to an authority-free HUD renderer. The pointer adapters have exactly one wiring path each, through the passive board view; they hold no session-side type and offer no second, non-passive way to be configured. There is no legacy controller for the composition root to reject.
- The application service accepts typed commands and explicit choices by stable rules identity, delegates to the existing authorities, and publishes accepted/rejected results, ordered events, and one immutable versioned match projection. Live play, deterministic replay, Undo, and restart use the same command path.
- Unity presentation follows Model-View-Presenter inside a ports-and-adapters boundary. Feature presenters translate view intent and immutable session projections; every enabled pending-decision surface binds the exact command object from the standing application contract, while passive views render immutable view models and never own legality, pending continuations, snapshots, or authoritative state.
- One small scene composition root performs Unity object discovery and dependency wiring. Feature components do not use a singleton, service locator, global event bus, or direct cross-presenter calls.
- Board interaction, director hands/commitments, round/action state, Undo/restart controls, and diagnostic log projection remain separate presenter/view responsibilities. No replacement component may combine all session ownership, history, input, projection, and rendering responsibilities.
- HUD source follows those feature boundaries under `Assets/GuardsDigital/Presentation/Match/`: each feature view has its own file, with feature presenters/models alongside it. `BoardInteractionModels.cs` and `RoundActionModels.cs` hold the larger immutable model groups. `UiToolkitMatchHudViews.cs` retains shared drawing helpers; `MatchFeaturePresenters.cs` retains shared choice labels/binding and coordination. Moving types between these files must preserve their public identities and assembly boundary.
- Unity-native resources created by presentation have one explicit owner, are reused while that owner lives, and are destroyed or disposed with it. Saved asset references are never destroyed as if generated. Repeated configured-map rebuilds reuse stable tiles, markers, minion views, materials, and fallback meshes rather than creating monotonic native-object growth.
- The destination-highlight Material uses an explicit generated-versus-assigned ownership contract. One generated instance is reused for the owning configured scene or unconfigured drill lifetime and only that generated instance is destroyed at teardown; an injected or saved Material is never destroyed by presentation.
- Unchanged feature refresh/repaint paths reuse immutable view models, definitions, offers, lookup collections, labels, and GUI styles. Mechanical architecture tests protect pure-assembly Unity independence, session-port/presenter/view dependency direction, composition-root-only discovery, supported Unity discovery APIs, and the prohibition on rules branching or parsing by display name/printed text.
- Milestone 8.30 placed match authority behind `IMatchHost`, the transport-neutral port on this application boundary: the local director adapter and a future network host submit the same typed commands to it and consume one ordered result stream from it, and owner-authorized projections build on the same port at 8.30a. Network callbacks do not become rules authorities, and local director-only tools remain outside competitive client projections.

### Private-online decision constraints

Milestone 8.29 selected and pinned the minimum provider, dependency, protocol, trust, compatibility, failure, privacy, and removal boundaries in [PRIVATE_ONLINE_ARCHITECTURE.md](PRIVATE_ONLINE_ARCHITECTURE.md). This section retains the measured implementation constraints that decision consumes.

- Milestone 8.28a verifies that `GuardsDigital.Core` and `GuardsDigital.Application` remain free of Unity references. One authoritative host may therefore own the existing synchronous `IMatchSession` without moving rules into URP, a scene, or a transport callback. The host must serialize session mutations through one executor; no current contract promises concurrent `Execute`, restore, or lazy projection access. Milestone 8.30 built that executor rather than leaving it a constraint: `MatchHost` admits one submission at a time, refuses a submission made from inside another before the authority is reached, and appends each accepted one to a bounded ordered result stream that reports an out-of-window cursor as requiring resynchronization.
- `MatchSessionProjection` is a full-trust director read model, not a client wire contract; milestone 8.30a added `SeatProjection` beside it, one per seat, and left this one unchanged. It contains all 108 card instances and definitions, the complete accepted-command history, whole-match diagnostics, and both authoritative and diagnostic snapshot access. A private client contract must omit another seat's hand, pre-reveal commitment identity, director history/Undo/restart, full snapshots, and sensitive diagnostics structurally rather than transmit them for a view to hide.
- `DirectorCommand` identifies the requested rules operation but carries no trusted caller, session identity, unique submission identity, or expected projection version. A future submission envelope must derive caller/seat/hero/team from the host's trusted connection binding, carry unique-command and expected-version data outside the gameplay payload, and let `MatchSession` remain the final rules-legality authority. Its host adapter must admit only the owner-scoped offered command surface; forwarding an arbitrary typed `DirectorCommand` is not authorization.
- The compatibility tuple for a private session includes the match/session identity still to be designed, immutable player/hero ownership, projection version, snapshot schema v34, selected map ID/revision, and every registered content revision. Snapshot restore requires the matching initial configuration/catalog; clients do not become snapshot authorities. Milestone 8.29 must select and pin the transport/protocol version boundary and explicit mismatch behavior without weakening the existing reject-instead-of-rebind rules.
- Each immutable projection publishes at most one genuine pending-decision contract, with one stable family ID and its exact ordered `DirectorCommand` answers. A transport representation must preserve that family/choice identity and ordering, identify the authorized chooser or team through the owner-scoped projection, tolerate stale delivery through expected-version rejection, and never treat a projected answer as pre-authorization.
- At the reviewed six-player scale, fixed seed 5 completes in 799 accepted commands and emits 3,487 command events plus one setup diagnostic event over 12 rounds. The final authoritative payload is 37,339 decoded bytes; the bundled payload including the full diagnostic log is 623,853 decoded bytes. Full-prefix replay measured 2.119 seconds on the .NET diagnostic tier, while restoring the bundled final state measured 40.485 ms and retained-point Undo remains below 150 ms. These figures make snapshot-based host recovery suitable for architecture comparison, but prohibit treating the growing director diagnostic bundle or full replay as a per-command client synchronization payload.
- The accepted URP player evidence remains a client-presentation boundary: 60 steady frames measured 9,967 B maximum managed allocation per frame, 3.569 ms p95 frame time, 15 owned resources with zero growth, 0.382 ms average snapshot capture, 8.042 ms average accepted-command refresh, and 45.322 ms Undo. A networking choice must preserve URP 17.5/build compatibility, but render frames, Unity objects, and client latency never gate or determine authoritative rules progress.

### Undo and diagnostics

- Director-mode Undo must retain one immutable initial-scenario description plus a typed log of accepted gameplay commands and explicit choices. It removes the latest command, reconstructs authority, and deterministically replays the surviving prefix through the normal command paths. Since milestone 7.9b the reconstruction starts from the most recent retained point at or before that prefix rather than from setup, so the replayed segment is bounded by the checkpoint interval instead of by match length.
- A retained point is the aggregate's own serialized pre-image, kept every fixed number of accepted commands at the cost of three references. It is a derived cache that a restore, a replay and a rollback can each discard and rebuild; the command log stays the one authority Undo answers from, and no inverse-action handlers exist. Undo rebuilds presentation and the read-only diagnostic event log from the reconstructed authority and replayed accepted events.
- Full-match undo history is acceptable for the small internal prototype.
- Undo, hidden-state inspection, and Tie Breaker override are internal tools and unavailable in competitive online matches.
- The implemented history contains typed accepted commands only. Invalid and presentation-only inputs create no entry; restart clears the command log and rebuilds the immutable initial scenario. Redo is intentionally absent.
- A player-facing save system is not part of the pitch.
- Internal authoritative snapshot capture/restore and the collapsible read-only event log remain implemented. Snapshots remain available for persistence, diagnostics, and later network resynchronization, while Undo/restart uses command replay. Planned tools still include animation-speed control.
- Diagnostic snapshot envelopes use bounded, non-throwing typed rejection and never partially restore malformed input. The durable schema-version-52 compatibility corpus pins representative setup, active-turn, Movement-choice, end-of-round, hero-or-minion selected Minion-Battle-choice, placed-token, attached-marker, pending-correction, current-round hero-Defeat, repeated-Attack exclusions, modal-bullet continuation scope, suspended borrowed-Skill parents and a spellbook with a removed spell; attached-marker rows now also retain a numbered turn-slot association. It also retains whether a correction still owes a repeated action instance, every remaining minion's current board coordinate, mutable remaining-minion identities, Defeat-reward balances/outcome idempotency, combat timing/value discriminators, and the round-owned Minion-Battle/Lane-Push continuation vocabulary. Each superseded schema or content identity is explicitly rejected rather than reconstructed or rebound. Completed-match data remains explicitly unsupported until its authority exists, and every incompatible durable schema/content-identity change requires a same-milestone migrate-or-reject decision.

### Card system

- `Docs/AI/CARD_SYSTEM_ARCHITECTURE.md` is the required card/resolver contract. The `Docs/AI/CARD_EFFECT_CAPABILITIES.md` index and its routed shards are the mandatory effect/keyword companion for all mutation, query, modifier, token, marker, timing, and system-transition work.
- The architecture must support the future hero catalog without claiming that unknown cards require zero extensions.
- Immutable, revisioned `CardDefinition`-equivalent content is separate from owned runtime `CardInstance`-equivalent state. Instances refer to definitions; definitions are never mutated into match state or upgrades.
- Runtime card lifecycle is represented through orthogonal facts such as location, played status, resolution status, and face orientation because the rulebook permits overlapping states.
- A card and an action are not the same selection. Immutable action definitions hold structured printed/general rules content; runtime action offers bind a definition to the current actor, source card, state, and invocation context. Offers explicitly distinguish printed Primary, printed Secondary, general-rule Secondary, replacement, reaction, repeated, and card-text-granted use, including whether card text applies.
- Printed icon values are queried through typed value/contribution services so later items, card text, minions, and active effects can modify totals without replacing early card models.
- Ordered action execution is deterministic and resumable. Mandatory/optional steps, target and modal choices, repeats, nested Defense, timing windows, and active effects use serializable rules data rather than delegates, coroutines, or UI-owned state.
- Targeting, presence checks, value calculation, card-state transitions, timing, and active-effect lifetime are reusable rule services rather than card-specific UI logic.
- Passive/continuous rules sources, including Ultimates and persistent token properties, remain distinct from ordinary cancelable Active effects.
- Common effects compose small typed definitions/handlers. A genuinely unique verified effect may register one isolated pure-code handler, but it must use the same validation, pending-choice, event, timing, state, and serialization boundaries.
- The shared action dispatcher owns cross-action resolution identity, authoritative offer revalidation, atomic rejection, serializable pending-choice publication, restoration coordination, and ordered-event publication without implementing a backend algorithm. Milestone 6.1h removed the explicit typed strategy registry the dispatcher had been decomposed behind - every interface had exactly one implementation and no consumer existed beyond the registry - so the dispatcher calls the distinct concrete Movement and Attack/Defense backends directly; they own their handler-specific pending state, validation, restoration, mutation, and typed results. Effect capability dispatch remains the separate data-driven seam implemented at 6.2a because capability references arrive from trusted definition data. Its generic Core factory contains no verified-hero reference; the build composition root supplies verified declarations to the one deterministic catalog.
- Each reusable effect/query has a stable versioned capability ID and typed contract covering source/actor/chooser/target roles, optionality, atomicity, state changes, checkpoints, events, continuation data, validation, and tests. Every enum-like integer parameter declares its immutable legal domain, and an independent owner-identity oracle covers every configured hero's reachable action, Ultimate, triggered, and active semantics.
- Every effect node has its own stable node ID and typed input/output bindings. Serializable outcomes record actual targets, path/distance, stopping reason, defeat/removal/prevention, resource changes, and other facts so later text can branch on real results without callbacks or a universal expression language.
- Object Push, direct Move, Place, Spawn, Respawn, Swap, Replace, Remove, and Defeat remain distinct public capabilities even when they share spatial helpers. Tokens and markers have distinct instance, supply, occupancy/attachment, and lifetime rules.
- Card text such as `move a unit towards you` uses direct Move plus source-relative `Closer` destination constraints, not a separate Pull capability.
- Rules objects preserve both intrinsic representation kind and derived effective type. Each capability declares which it queries, including the rulebook exception that after-action Battle-Zone correction applies to minion miniatures rather than objects that merely count as minions.
- System consequences use typed operation facts/checkpoints: only Defeat/Remove can immediately advance the Lane, while Move/Object Push/Swap cannot; displaced-minion correction runs after the whole action.
- Never branch rules on card display name, hero display name, image filename, or printed text. Do not build a runtime natural-language parser or speculative universal scripting language.
- Phase 1 proves this foundation with placeholder definitions/instances, explicit Movement offers and typed values, command/events, a resumable choice shell, and visible card-driven movement.
- Phase 2 proves extension by opening a basic Attack, pausing for the target hero's Defense reaction, discarding one owned card or declining, and resuming the unmodified comparison through the same authority.
- Phase 3 proves generic card lifecycle, director hands, play/reveal, Initiative and tied Initiative, Hold, Movement and Attack inside turns, the four-turn round skeleton, an extensible repeated-round transition with limited synthetic retrieval, snapshots, Undo/restart, and event logging with synthetic definitions.
- Phases 4 through 7 prove the official map, core full-map actions and combat, minions, tokens, Lane Push, exact end-of-round order, defeat/respawn, progression, victory, and a deterministic complete match with synthetic definitions.
- All six configured heroes' complete playable inventories compose through the shared core loop and typed extension seams; the permanent player-path gate rejects hero-name rule branches.
- Complete Wasp verification remains an intermediate integration gate. Only afterward are five additional heroes selected, inventoried, capability-mapped, implemented, and integrated into the official-setup 3v3 pitch match.
- Add reusable primitives only when a verified rule or card requires them. Later discoveries may require a localized capability, handler, or explicit schema migration, but must not silently rewrite ownership, action context, UI authority, or continuation semantics.
