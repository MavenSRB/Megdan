## Configured presentation surfaces

Corrective milestone 5.1a increases each of the ten explicitly synthetic test-card Movement values by one while preserving every other card value and stable definition ID. Its content revision advances so older synthetic snapshots reject instead of silently acquiring the new values. The configured passive HUD now clamps its card panel to the available viewport and scrolls the hands/action body below its fixed header, keeping projected Defense-card and Decline controls reachable for the reported 778-by-300 geometry without changing Defense legality or command authority.

Corrective milestone 5.1b makes every configured legal Defense-card invocation label contain the authoritative card display name and typed printed Defense value under the explicit `PRINTED DEFENSE` qualifier. Corrective milestone 5.1c removes the configured passive view's clipping 150-pixel Defense width, derives each Defense-choice minimum width from the complete label and current GUI button style, and expands the normal desktop card panel to 1280-by-360 while preserving viewport clamping and scrolling on short windows. The same projected typed commands, legal offer set, unchanged `DECLINE DEFENSE` invocation, and compact fallback remain authoritative; presentation does not calculate a modified Defense Total, infer eligibility, or resolve the reaction. Deterministic layout coverage and a visible non-batch 2048-by-1152 Game View capture confirm the four-card turn-one Defense set plus Decline are simultaneously readable without clipping, overlap, or scrollbars.

Milestone 5.8b adds a pending-response-only immutable Defense-preview projection. It carries the complete ordered Attack contribution list/total, one authority-computed preview for every legal Defense card plus Decline, complete ordered Defense contributions, optional Defense Total, explicit Block result, predicted outcome, and readable typed-source labels. The application uses the same pure Defense query and shared typed comparison factory as command resolution; presentation only formats those facts and retains the existing resolution/choice-qualified one-click commands. Hover or keyboard focus shows one opaque pointer-pass-through popup with explicit `ATTACK:`, `DEFENSE:`, and `RESULT:` sections; switching choices updates it, bounded leave delay dismisses it, and version changes clear it. The popup remains clear of its control and inside the viewport, using compact columns for longer breakdowns.

The same pending projection independently supplies the exact signed `MinionId` set from the already-calculated minion Defense modifier even when Decline is the sole choice. The passive board gives contributing minions persistent board-facing `+1` or `-1` text cues with smaller signed text, vertically oval dark-grey backings, and distinct restrained green/red sign colors, so sign never depends on color alone and remains separate from selectable Attack-target tile highlights. The number-only local horizontal inversion corrects the inherited token orientation; renderer-bounds compensation preserves horizontal centering, and a reviewed downward optical offset corrects the font's visually high vertical placement without changing the symmetric backing or adding an input surface. Cues remain stable across preview changes and rebuild only from a new immutable projection after response completion, rejection, Undo, restart, or restore.

Milestone 5.8a extends the configured passive board from Hero-only Attack intent to the same pending choice's authoritative `LegalTargetMinionIds`. The board view model carries current minion occupancies and exact legal identities; the retained target-highlight material marks their projected spaces, and generated minion pointer selectors forward only stable `MinionId` intent through `BoardInteractionPresenter`, `IMatchSession`, and the existing resolution/choice-qualified command. Presentation performs no team, distance, Range, Heavy-immunity, reward, Defeat, or removal calculation. Accepted authority removes the minion from the next application projection; the passive view disables that retained minion object and can re-enable it from a later authoritative projection such as Undo/restore. Existing Hero target and Defense continuation paths remain unchanged.

Corrective milestone 5.8a1 makes the configured minion presentation reload-safe. Each generated `StandardMinionView` serializes its stable binding `MinionId` independently of transient setup objects, so editor backup/domain restoration can retain and reconfigure the correct object. When the grid deliberately destroys/replaces views, it publishes the complete current set only after rebuilding; the composition root atomically replaces `BoardInteractionUnityView` and `PrimitiveHeroPointerInput` bindings, creates/configures exactly one selector and collider per view, and removes destroyed references before any later session refresh. Rebuild, Play Mode entry, scene reload, commitment, target refresh, removal, Undo, restart, and restore retain the same twelve configured identities without `MissingReferenceException`, duplicates, or presentation-owned legality.

Milestone 6.1a adds the player-facing Minion Battle removal choice over milestone 6.1's unchanged authority. A sixth passive view/presenter pair - `IMinionChoiceView`, `MinionChoiceUnityView`, and `MinionChoicePresenter` - builds its whole model from the immutable pending choice: chooser team and identity, required count, current selection, one control per candidate the choice currently offers a select or deselect invocation for, and a confirmation control only while the choice reports `CanConfirm`. A candidate the authority withholds, which is how a Heavy appears while a non-Heavy is unselected, carries no control at all, so presentation never reproduces the Heavy-last ordering that withheld it. Controls read `REMOVE`/`KEEP` plus team, intrinsic type, and the candidate's ordinal in the projection's own candidate order, and the `CONTINUE END OF ROUND` control is withheld while a choice stands because the authority rejects that advance. Pointing at or focusing a control reports one stable `MinionId` to `BoardInteractionPresenter`, which resolves it against the projected candidates and marks that minion with a board cue reusing milestone 6.1b's reviewed proportions; the highlight is anchored to the projection it was read from, so an accepted command, refusal, restore, replay, or Undo drops it. Milestone 6.1ao settled that cue's content: both visible kinds draw one downward-pointing marker at a declared character size and differ only in color, because both mean "this minion" and only the control state behind them differs, so the cue view model carries no per-cue text and candidate identity stays in the control labels. Submitting matches the control against the current projection and forwards only that projected typed invocation through `IMatchSession`; a stale or refused control executes nothing and rebuilds the visible selection from the returned projection.
