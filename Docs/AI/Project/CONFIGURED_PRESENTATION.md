## Configured presentation surfaces

Corrective milestone 5.1a increases each of the ten explicitly synthetic test-card Movement values by one while preserving every other card value and stable definition ID. Its content revision advances so older synthetic snapshots reject instead of silently acquiring the new values.

Corrective milestone 5.1b makes every configured legal Defense-card invocation label contain the authoritative card display name and typed printed Defense value under the explicit `PRINTED DEFENSE` qualifier. Corrective milestone 5.1c then removed the clipping 150-pixel Defense width that label had outgrown. Milestone 7.8a keeps that guarantee and makes it structural rather than measured: a contextual control is content-sized and no width, maximum width, or truncation is assigned to one anywhere, so a complete label cannot be cut off by a width nothing set. The same projected typed commands, legal offer set, unchanged `DECLINE DEFENSE` invocation, and compact fallback remain authoritative; presentation does not calculate a modified Defense Total, infer eligibility, or resolve the reaction. Deterministic layout coverage and a visible non-batch Game View capture confirm the four-card turn-one Defense set plus Decline are simultaneously readable without clipping, overlap, or scrollbars at the validated 2048-by-1152 desktop size and the reported 778-by-300 short-viewport fallback.

Milestone 5.8b adds a pending-response-only immutable Defense-preview projection. It carries the complete ordered Attack contribution list/total, one authority-computed preview for every legal Defense card plus Decline, complete ordered Defense contributions, optional Defense Total, explicit Block result, predicted outcome, and readable typed-source labels. The application uses the same pure Defense query and shared typed comparison factory as command resolution; presentation only formats those facts and retains the existing resolution/choice-qualified one-click commands. Hover or keyboard focus shows one opaque pointer-pass-through popup with explicit `ATTACK:`, `DEFENSE:`, and `RESULT:` sections; switching choices updates it, bounded leave delay dismisses it, and version changes clear it. The popup remains clear of its control and inside the viewport, using compact columns for longer breakdowns.

The same pending projection independently supplies the exact signed `MinionId` set from the already-calculated minion Defense modifier even when Decline is the sole choice. The passive board gives contributing minions persistent board-facing `+1` or `-1` text cues with smaller signed text, vertically oval dark-grey backings, and distinct restrained green/red sign colors, so sign never depends on color alone and remains separate from selectable Attack-target tile highlights. The number-only local horizontal inversion corrects the inherited token orientation; renderer-bounds compensation preserves horizontal centering, and a reviewed downward optical offset corrects the font's visually high vertical placement without changing the symmetric backing or adding an input surface. Cues remain stable across preview changes and rebuild only from a new immutable projection after response completion, rejection, Undo, restart, or restore.

Milestone 5.8a extends the configured passive board from Hero-only Attack intent to the same pending choice's authoritative `LegalTargetMinionIds`. The board view model carries current minion occupancies and exact legal identities; the retained target-highlight material marks their projected spaces, and generated minion pointer selectors forward only stable `MinionId` intent through `BoardInteractionPresenter`, `IMatchSession`, and the existing resolution/choice-qualified command. Presentation performs no team, distance, Range, Heavy-immunity, reward, Defeat, or removal calculation. Accepted authority removes the minion from the next application projection; the passive view disables that retained minion object and can re-enable it from a later authoritative projection such as Undo/restore. Existing Hero target and Defense continuation paths remain unchanged.

Corrective milestone 5.8a1 makes the configured minion presentation reload-safe. Each generated `StandardMinionView` serializes its stable binding `MinionId` independently of transient setup objects, so editor backup/domain restoration can retain and reconfigure the correct object. When the grid deliberately destroys/replaces views, it publishes the complete current set only after rebuilding; the composition root atomically replaces `BoardInteractionUnityView` and `PrimitiveHeroPointerInput` bindings, creates/configures exactly one selector and collider per view, and removes destroyed references before any later session refresh. Rebuild, Play Mode entry, scene reload, commitment, target refresh, removal, Undo, restart, and restore retain the same twelve configured identities without `MissingReferenceException`, duplicates, or presentation-owned legality.

Milestone 6.1a adds the player-facing Minion Battle removal choice over milestone 6.1's unchanged authority. A sixth passive view/presenter pair - `IMinionChoiceView`, `MinionChoiceUnityView`, and `MinionChoicePresenter` - builds its whole model from the immutable pending choice: chooser team and identity, required count, current selection, one control per candidate the choice currently offers a select or deselect invocation for, and a confirmation control only while the choice reports `CanConfirm`. A candidate the authority withholds, which is how a Heavy appears while a non-Heavy is unselected, carries no control at all, so presentation never reproduces the Heavy-last ordering that withheld it. Controls read `REMOVE`/`KEEP` plus team, intrinsic type, and the candidate's ordinal in the projection's own candidate order, and the `CONTINUE END OF ROUND` control is withheld while a choice stands because the authority rejects that advance. Pointing at or focusing a control reports one stable `MinionId` to `BoardInteractionPresenter`, which resolves it against the projected candidates and marks that minion with a board cue reusing milestone 6.1b's reviewed proportions; the highlight is anchored to the projection it was read from, so an accepted command, refusal, restore, replay, or Undo drops it. Milestone 6.1ao settled that cue's content: both visible kinds draw one downward-pointing marker at a declared character size and differ only in color, because both mean "this minion" and only the control state behind them differs, so the cue view model carries no per-cue text and candidate identity stays in the control labels. Submitting matches the control against the current projection and forwards only that projected typed invocation through `IMatchSession`; a stale or refused control executes nothing and rebuilds the visible selection from the returned projection.

Milestone 6.4b routes the displaced-minion correction through that same interface rather than a second prompt framework: the one view model gained a prompt kind - Minion Battle removal, correction subject, correcting Move, fallback Place - and the presenter's submit, confirm, and stale-refresh paths never branch on it. A correction prompt is addressed by the owning action's identity, names the displaced stable minion, and offers one control per projected candidate: the deciding team's displaced minions at the subject stage (the correction-order amendment), or the exact equal-shortest route endpoints or equally-nearest Place spaces at the destination stage, labelled `RETURN`, `MOVE TO`, or `PLACE AT` so removal, correcting Move, and fallback Place stay distinguishable, with the shared gutter naming the family from the model. Selection is the advance, so a correction carries no separate confirmation. The board adapter lights a projected destination through the same highlight material Movement and Fast Travel use - since milestone 6.2d the one whose control is currently pointed at rather than all of them at once - and marks the displaced subject with the selected cue throughout a destination choice; clicking a space, lit or not, forwards only the projected invocation - presentation calculates no path, distance, Battle-Zone membership, occupancy, or Tie-Breaker ordering. Deterministic no-choice corrections render no prompt at all, and Actions, Fast Travel, and End Turn are withheld while a correction stands, because the authority holds the action open until it completes. The configured-scene driver gained the coordinate-valued submitters 6.8k deferred to this consumer: an effect-frame value candidate, a correction subject, and a correction destination are each addressed by what they select.

Milestone 6.5c gives a paused effect frame's decision the surfaces the rest of the configured match already uses, and splits them on the option/value distinction the authority itself draws rather than on any card. A mode candidate keeps the control milestone 6.8a gave it, including its explicit confirm. A value candidate that names an empty space carries no control at all: the board lights every such candidate with the one highlight material Movement, Fast Travel, and corrections share, and clicking a lit space forwards that candidate's projected select invocation together with the confirm the authority offers immediately afterwards, so an exactly-one choice is answered in a single click without presentation composing a command of its own. A value candidate that names a board object carries one control labelled after that object - the configured display name for a hero, the projected team and intrinsic type for a minion, and since milestone 6.2d the projected definition's display name for a token, with the candidate ordinal kept only where the same name would otherwise be offered twice - and pointing at or focusing that control marks the object with milestone 6.1ao's downward marker, now shared by the hero view as well as the minion view, and lights the space the authority projects the consuming operation would leave it on in a second, distinctly dark highlight material that is never selectable. A zero-space Push marks the target's own space, since standing still is a legal result rather than a refusal. Both cues are anchored to the projection they were read from, so an accepted command, refusal, restore, replay, or Undo drops them, and a control whose candidate the current projection no longer offers submits nothing.

That preview is authority-computed, the way milestone 5.8b's Defense preview is: the projection carries, per space-valued candidate, the board object standing there and the space a consuming Push would leave it on, derived by reading the paused frame's own definition graph for the node that binds this choice's output and asking the same displacement query command resolution asks. Presentation derives no direction, distance, occupancy, or obstacle result, and no label or branch reads printed card text or a card, hero, or node name.

Milestone 6.5b adds the third arm of that split, for the value kind naming a piece that stands nowhere: a Spawn candidate names a miniature in the supply, which no board cue can point at and no highlight can light. It is a control like a mode, labelled from the declared setup roster's team and intrinsic type in the same form a standing minion's control uses, so a supply candidate and a board candidate read alike instead of one of them falling back to an ordinal. Nothing else about the branch reaches presentation: its destination is the miniature's own declared Spawn point rather than an offer, so there is nothing to light and nothing to confirm beyond the choice itself.

Milestone 6.2d gives a placed token a surface and retires milestone 6.2's decision that presentation receives no token projection. `MatchSessionProjection` carries the board authority's own placed-token instances - stable identity, coordinate, and the trusted definition object the catalog supplied - so a reader names a token from projected state and no presentation type holds a component catalog reference. The configured scene deals five cards per hero, the same five the default configuration every pinned digest and card-matrix assertion measures. Milestone 6.2d had dealt milestone 6.2's Cache card beside them as a sixth, because it was then the only route by which a player could put a token on that board; Blue Feint carries all three of that card's modes now, so the placement is a mode of the hand rather than a sixth card. It is on Feint rather than on Blue Sentinel, whose Swap/Replace/Remove family it belongs to, because rulebook p.8 removes every placed token at the end of a round and a card is played at most once in a round: a Sentinel supplying its own Hazard would never have one standing when it returned to hand. Feint at Initiative 12 and Sentinel at 11 are two cards of one hand, so a single round still holds the play that places the token and the play that acts on it. A projected token is drawn as a flat disc under a board-facing name at its coordinate, smaller than a unit and lower, carrying no pointer selector because a token is named by a prompt control and marked by its space. Its views follow the retained discipline hero and minion views follow, reached the only way a runtime-minted identity can reach it: a view is built the first time an instance is seen, bound while that instance is projected, released and hidden when it is not, and rebound when it returns, so removal, replacement, Clear, restore, replay, and retained-prefix Undo all redraw rather than leave a hole, and a projected token the board cannot bind is the same loud fault a projected minion without a view is. A Replace needs no separate handling, because both halves arrive in one projection and the space is never drawn empty between them.

The same milestone makes a destination highlight follow the pointer wherever the destination carries its own control. The pending correction's endpoints are that case: each already draws a `MOVE TO` or `PLACE AT` control, and lighting all of them at once said only that several spaces were involved. The board view model now carries a single nullable correction destination rather than a list, which is the shape the Hero Respawn highlight already had, and the prompt reports the whole pointed-at candidate rather than its unit alone - every candidate of a destination prompt shares the one displaced subject, so the unit could not tell them apart. The other families that draw one control per destination already behaved this way: Hero Respawn options and milestone 6.5c's named target controls each report a single pointed-at control. A candidate whose only surface is the board keeps its standing highlight, because there the lighting is the affordance and clicking the space is how the choice is answered; Movement, Fast Travel, and the effect choice's empty-space candidates are unchanged. Which spaces are legal, which one a click answers, and what any command carries are all exactly as before.

Corrective milestone 6.3a gives milestone 6.3's implemented Clear the surface that milestone deliberately left out, and routes every control that names a token back to the piece it means. The projection carries one Clear option per currently available replaceable Attack - bound to that exact source card, actor, and replaced action - together with the adjacent tokens the existing authority query admits and the exact canonical `PerformClear` invocation for every confirmable subset, the empty one included, because p.13 permits any number and milestone 6.3 already accepts none. The configured action row draws `CLEAR (REPLACES ATTACK)` beside the card's other legal actions; a card with no current replaceable Attack draws nothing, which is a projected fact rather than a view's decision. Opening the selection accepts no command and changes no authoritative state: it draws one control per offered token, labelled from the projected definition by the same rule every other token control uses, plus `CONFIRM CLEAR` and `CANCEL CLEAR`. The presenter tracks only which projected candidates are selected, matches that set to one projected invocation, and forwards it unchanged - it derives no adjacency, eligibility, or replacement legality and composes no payload - and the confirm joins the legality set the round presenter validates every submission against. Cancelling submits nothing and leaves the card unresolved and the action choice untouched; the open selection is anchored to the projection it was read from, so a projection-version change, an accepted or refused command, End Turn, Undo, restart, restore, or replay drops it and rebuilds from current state.

The same milestone makes a token a thing the board can point at. A control whose candidate names a token reports the stable `TokenInstanceId` rather than a display name or a coordinate, and the board resolves that identity against the current projected token list alone, so presentation never reads occupancy back out of a space and a stale control naming a piece that has moved, been replaced, or been removed marks nothing. `PlacedTokenView` carries the shared board-facing cue construction and milestone 6.1ao's two treatments: the piece a control is pointed at or keyboard-focused on wears the pointed-at marker, and a token selected into a Clear subset keeps the selected marker while the pointer moves across the other controls, with `Selected` outranking `Highlighted` exactly as it does for a minion. The same path covers milestone 6.5c's existing token-valued effect controls, which is milestone 6.6a's handoff finding closed: Blue Sentinel's Remove and Replace targets read `TEST - HAZARD` and marked nothing, because this view had no cue to set. The cue is distinct from destination highlighting and from any clickable board affordance - a token still carries no pointer selector - and it is dropped or rebuilt on confirmation, cancellation, refusal, projection change, restore, replay, and Undo.

## Maintenance rule

Corrective milestone 6.5aa widens the Minion-Battle surface from `MinionId` to projected hero-or-minion `RuleObject` candidates, so a counts-as hero receives the same authoritative remove/keep control and downward board cue without presentation deciding its effective type. It also adds the p.7 Hero Respawn surface: one button per authoritative destination plus `RESOLVE WITHOUT ACTION`. Pointing at or keyboard-focusing a destination button previews exactly that coordinate using the same board highlight material as Movement; exit/blur clears it, and stale projection identity cannot submit or retain the preview.

Corrective milestone 6.5ab makes hero visibility projection-owned in the same retained-view style as minions. If a configured hero identity has no occupancy in the current projection, the board clears its cue and deactivates that hero GameObject and collider. If the identity returns through Respawn, Undo, restart, or restore, the board reactivates the same view and configures its new authoritative coordinate; presentation creates no removal or respawn rule of its own.

Corrective milestone 6.5ac gives that decision one more shape: an option the acting player cannot perform. Which options those are is projected by the authority and never inferred here. Such an option keeps its label and its ordinal and is drawn as a disabled control beside the ones that can be taken, so a player reads that the mode exists and cannot be chosen; there is no reason text, by the 2026-08-16 user decision recorded as open rules question 11. It carries no command at all rather than a refused one, which is why it is a view-model shape of its own, and the round presenter refuses any command naming it even when one survives on an older model. Corrective milestone 6.5af applies the same treatment one level out, to an action offer. A Skill the authority judged unstartable keeps its label and its place among the actions and is drawn as a disabled control carrying no command, so a player reads that the action exists, cannot be taken, and that the card's other actions and Hold are still theirs. Which offers those are is projected, not inferred here, and the round presenter refuses a start naming one even when a command survives on an older model.

Corrective milestone 6.5ae then gave that decision its own way out. Where no option of a mandatory choice can be performed, every option is drawn greyed and the authority projects one command: presentation renders it as the same End Turn control a paused Movement's stop has always used, and forwards it only when the player clicks it - never on a timer, and never as a consequence of any other command. Every other control stays withheld exactly as before, so End Turn is the only thing on screen that does anything, and nothing about the paused decision moves until it is taken.
