## Current implementation

### Application, configured presentation, and governance

The project has completed roadmap milestones through **6.4c**. Earlier phases established the corrected and independently verified Phase 4 architecture/performance gate, deterministic command-replay Director Undo, the internal rule-event log, the reviewed `official-single-lane` revision 1 map and exact setup, map-bound snapshots, authoritative zone/Lane queries, the pure application port, distinct Movement/Attack-Defense/Fast-Travel/Clear handlers, cached feature projections, bounded diagnostics, and configured saved-scene MVP/input cutover. The configured scene has no legacy controller: its composition root creates the bounded session, peer presenters/passive views, authority-free HUD, and passive board callbacks.

One dispatcher owns live typed commands, replay, Undo/restart, restore, ordered events, and immutable projections, while five concrete backends own handler-specific pending state and mutation and are reached by direct composition rather than through a registry. Action-kind dispatch is that direct composition; capability dispatch alone is data-driven lookup through `EffectCapabilityCatalog`, because a capability reference arrives as data inside the definition the resolver is walking and cannot be named at compile time. The contextual End Turn control forwards only a projected stop - the Hold, the Movement Stop, or an effect choice's own - and is suppressed during every mandatory choice that projects none. Action offers carry a decided availability rather than an assumed one: the card query that builds them reads card state alone, and the turn authority stamps a Skill unavailable where the same feasibility walk proves its whole effect can apply nothing, which the offer set and the start command both consult, so an action the rules can prove would do nothing is drawn greyed and cannot be started. p.12 is the source - Hold exists so that a player is never forced to perform an action - and the turn stays spendable on the card's other actions.

A Skill is an ordinary printed action offer resolved over an immutable, catalog-owned `EffectDefinition`: a flat table of stable nodes with `Sequence`, `Optional`, `Conditional`, `Choose` and `RepeatAction`, where `Mandatory`, `may`, `up to` and `if able` stay four distinct behaviors rather than one failure path. `PendingResolution` carries identity, a continuation stack, completed outcomes and accepted choices - references only, never an `EffectDefinition` object or a handler, so the snapshot written from it has nowhere to put semantics. Every decision inside an effect frame rides one `AnswerEffectChoice` command carrying the invocation the pending choice projected, including the token and marker decisions described below. Presentation forwards those invocations and nothing else: the round view renders a paused frame's projected options and withholds the actions, Fast-Travel offers and End Turn control the authority would refuse while it stands, except where the paused choice projects a stop of its own, which is rendered as that same End Turn control and never submitted for the player. The Skill seams hold the same bar as Movement and Attack: starting a Skill revalidates the offer against the authoritative offer set and invocation context through the shared Core prevalidation, and the effect-answer path prechecks pending identity and source-card state so a bad state rejects with a typed reason instead of faulting at completion. A Skill whose root completes during its own start resolves there rather than faulting: a start reads identity from the started resolution and offer, not from the frame that shape never produces, so choice-free Skills are writable and emit the ordinary started/node/completed stream. A `Choose` offers only the options the chooser can perform: each branch is walked in execution order and every capability in it is asked what it would report without performing anything, so a mode proven to apply nothing is projected but carries no selection and a stale or forged select naming it is rejected atomically. A mandatory node whose every option is refused pauses with all of them shown greyed and offers one command, the stop a paused Movement has always carried; accepting it ends the action with the same node result, ordered facts, card resolution and turn hand-off the unprompted stop produced, and nothing ends it until the player asks. An optional node in that position still declines without pausing, because there is nothing there to close. The stop is derived from the refusals and the node's own policy rather than stored, so restore, replay and retained-prefix Undo re-derive it or drop it as the state then stands. A branch that cannot be judged - a required input a later step publishes, or a predicate that would have to be executed - stays offered. A target selection closes most of that gap by declaring the node it selects for, as a typed literal naming another node of the same definition: candidate derivation asks that consumer the same question, once per candidate with the candidate standing in for the output it binds, so a selection offers only objects the effect can act on and a branch behind one whose consumer accepts nothing is refused before it is chosen. Eligibility is re-read when the answer arrives rather than trusted from the offer, and an answer naming a candidate the consumer would now refuse is rejected atomically with the pending choice left standing. A node reference is a definition-time address that no role supplies, no capability publishes, and no payload carries, and the definition validator rejects one naming a node the definition does not declare or one that reads nothing the selection publishes. The answer is never written: it is re-derived beside the candidate set at every pause and on restore, replay and retained-prefix Undo. Refusals report Skill-specific rejection reasons, Skill facts materialize under their own `SkillActionProgressed` turn event kind, a paused Skill frame suppresses the projected Fast-Travel options exactly as paused Movement and Attack do, and snapshot restore re-derives a paused capability's candidates with the node's input bindings rebuilt from the persisted completed outcomes through the resolver's own binding path. A definition can also ask for its own action to happen again. The `RepeatAction` node performs nothing and invokes no capability: it records the request as an ordinary applied outcome, the instance that made it ends normally with its own started and ended checkpoints, p.18's after-action correction runs to completion, and only then does the card-action dispatcher start a second instance of the same trusted action definition. That second instance runs under an explicit repeated invocation context, under which a `RepeatAction` node is ineligible and therefore skipped in silence rather than offered and refused - which is the whole bound, so no count and no depth are recorded. The node admits `may` and `if able` only, because a repeat that must happen is unbounded by construction. Nothing that reads offers can create one: the dispatcher's start gate admits the two printed invocation contexts alone, so a repeated instance is never a replaceable offer, and it reads the board, the modifications, the participants and the round for itself at the moment it starts rather than inheriting anything. The option-feasibility walk judges a repeat as applying nothing, because what it re-runs is the action being judged. The only thing that crosses the wire is a correction paused while a repeat is still owed, which is also the only state one survives a command in.

Board occupancy has one seam: an internal per-space index owns the one-obstacle-per-space rule for heroes, generic obstacles, minions, and tokens through a single collision-checked add, so a new occupant kind joins by declaring a typed occupant rather than a parallel mechanism, and per-kind identity validation stays with each kind. Reachability consumes that index through an authority-backed query entry. Timing checkpoints are resolver-emitted: a card action returns one ordered step stream interleaving its rule facts with the checkpoints it raises, and the turn authority materializes that stream without reading any fact's kind. The cross-platform dotnet harness compiles Core, Application, and the Unity-free Edit Mode tests unmodified, with a Unity-dependent exclude list acting as a build tripwire and a map-loader shim guarded by a parity fixture; scope and commands live in `Docs/AI/Testing/DOTNET_HARNESS.md`.

Per-milestone outcome, validation, and review evidence lives once in each commit body, addressed by SHA from the [Phase 6 archive](../Archive/Phase-Handoffs/PHASE_6.md).

### Movement and action architecture

The Phase 4 gate's fresh-task independent verification is closed, with `F44E-01` through `F44E-05` confirmed and no gate-blocking observation outstanding; its inspection record is indexed from the [Phase 4 archive](../Archive/Phase-Handoffs/PHASE_4.md). Segmented typed Movement continuation runs on the exact selected map: shortest and deliberately longer cumulative waypoint routes to the same destination commit their selected ordered adjacent steps through the configured match session, a typed evaluator applies prevention or a distance limit once at Movement-action start, and the effective allowance is captured in existing pending state for continuation, restore, replay, and Undo boundaries.

Fast Travel is a distinct typed replacement action on the match-session command path. It accepts empty destinations in the actor's current zone or a shared-border adjacent zone, requires no empty-space path, rejects non-adjacent zones and enemy hero/minion presence in either endpoint zone atomically, records ordered replacement/relocation/completion facts, resolves the played card, and suppresses source-card text even when replacing Primary Movement. The application projection exposes only currently eligible Fast Travel replacements and their authoritative legal destinations. The configured passive HUD shows an eligible replacement as a `FAST TRAVEL` button, leaving normal actions and an unhighlighted board as the default; only explicit button selection exposes that exact destination set. A highlighted coordinate then submits the existing typed `PerformFastTravel` command through `BoardInteractionPresenter` and `IMatchSession`; presentation performs no zone, enemy-presence, or destination-legality calculation. Replay and Undo use the same command path.

The registered backend split is sound for the implemented families. Movement and Attack/Defense retain their serializable pending continuations; Fast Travel and Clear are immediate replacement backends, while Skill owns the catalog-bound effect frame and its serializable pending continuation. Clear deliberately uses the existing direct replacement seam rather than implementing the still-deferred generic `ReplaceAction` effect node. The outer application/round/turn dispatch continues to enumerate authority-level command families, while choices inside an effect definition use the shared `AnswerEffectChoice` command.

### Minions, timing, combat, and rewards

The twelve configured standard-minion records bind directly into authoritative board state. Their stable identities, teams, intrinsic Melee/Ranged/Heavy types, map-qualified spaces, and coordinates now enforce one-obstacle-per-space construction, Movement destination/transit blocking, and relocation emptiness without a presentation-derived or parallel minion representation. A discarded Defense card's typed value now adds rulebook minion contributions with stable `MinionId` provenance: +1 per adjacent friendly Melee/Heavy, -1 per adjacent enemy Melee/Heavy, and -1 per enemy Ranged within radius 2. Decline/no legal card still produces no Defense Total. Restore and session snapshot loading rebind the immutable configured minion collection and revalidate pending Defense contributions without a schema-version change. Milestone 6.1s made that position authoritative mutable state: a sealed `MinionOccupancy` carries a minion's identity, team, type, spawn, current space and coordinate, and is replaced through `WithPosition` so reference-identity change detection in the presentation refresh path still holds. `QuickGameMinionSetupState` returns to setup-only duty, converted at the board-authority boundary. Authority-internal `TryCommitMinionMove` validates identity, playable-space membership, and index occupancy, replaces the list entry, keeps the 6.1r occupancy index synchronized, and reports a typed `MinionMoveResult`; no `DirectorCommand` or session exposure exists yet, because the consumers arrive with Object Push (6.4) and Lane Push (6.9-6.11). The snapshot writes each remaining minion's identity and current coordinate and restores the position from the stream rather than reconstructing it from setup placements, advancing `CurrentSchemaVersion` to 7 and explicitly rejecting v6.

Timing is pure named checkpoints plus a validated serializable Active-effect lifecycle. Definition content owns affected scope, trigger set, uniqueness key, `This Turn`/`This Round`/`Next Turn`/`Next Turn after Playing Cards` duration, creation/activation/expiration anchors, cancellation conditions, cross-round policy, and the declared modifications the effect supplies; an instance carries controller/team, affected hero, source card/action, creation order, phase, and activation anchors. Every live effect is visited at every checkpoint, and the context hero narrows only the identity-targeted concerns - activation targeting, triggers, and `AffectedHeroDefeated` cancellation - so a Hero-scoped effect reaches its own expiration window regardless of which hero is acting. Uniqueness suppression compares the declared scope identity rather than one global key namespace, so different controllers activating the same definition coexist. Dormant/active/ended state and Ultimate/token/marker continuous sources round-trip in the current schema, and typed lifecycle facts stay deterministic through live execution, restore plus continuation, replay, and retained-prefix Undo. Printed-text parsing and Wasp content remain absent; the current duration vocabulary permits expiration only at the turn-only and round checkpoints.

Defeat-reward accounting is pure and runs over the participant collection. A typed Defeat outcome names its stable source/target, defeated team, acting hero, and already-verified Defeat/Assist amounts; deterministic typed coin-gain operations record recipient hero/team, reward kind, minimum/failure contract, and before/after balances. The acting hero receives the Defeat award, every other friendly participant can receive the Assist award, duplicate outcomes and invalid/friendly sources reject without mutation, and all recipients are planned atomically before balances change. A linked removal result remains a separate fact, so prevented removal cannot erase or duplicate an awarded Defeat. Exact hero-Level/lowest-Tier amount derivation, Attack integration, persistence, and UI remain with their later owning milestones.

Enemy minions are part of typed synthetic Attack targeting. Non-Ranged requires adjacency; Ranged uses current typed Range; Heavy remains Immune while a friendly non-Heavy remains in the starting Battle Zone. A legal minion target skips Defense and hero-only Attack Total comparison, records ordered Defeat, 2-coin Melee/Ranged or 4-coin Heavy reward, removal attempt, and a removed-or-prevented result, resolves the attacking turn card, and mutates authoritative occupancy. That last result is decided by the same shared removal stage the standalone Remove asks, so a prevented removal keeps the Defeat and the collected coins, names no removed occupancy, states its own ordered fact, and leaves occupancy and the reserve alone; a completed one records p.8's Defeat cause when it empties a side out of the Battle Zone. No prevention source can answer yes yet, because the only one the rules express is immunity and an immune minion is never a legal target. Snapshot schema version 4 persists remaining-minion identities, reward balances, and awarded-outcome idempotency; version 3 rejects. The unconfigured compatibility drill remains explicitly minion-free and its current Movement-value/continuation regressions are green.

The verified general synthetic Hero Attack/Defense order is complete. Stable target validation precedes Action Start/Before Attack, typed Attack Total, defender-owned response, explicit Block-or-numeric comparison, After Attack, and action end. Non-Ranged adjacency and Ranged distance remain the shared target paths; printed, minion, item, card-text, and Active-effect contribution kinds retain typed provenance while only verified synthetic printed/minion values are populated. A successful Hero Attack records a reward-deferred typed Defeat outcome without removal, reward, Life, victory, or respawn consequences. Snapshot schema version 5 adds the durable timing/value discriminators and explicitly rejects version 4; the refreshed four-fixture corpus round-trips byte-identically.

### Match state, replay, and configured scope

Authoritative pure C# state currently covers map-scoped identity, the immutable selected map revision, participant `PlayerId`/`HeroId` relationships, initial Tie Breaker, synthetic hands whose size is fixture composition rather than a modelled rule - the default configuration deals five cards, the configured scene deals those five plus milestone 6.2's Cache card, and the Skill fixture deals eight - owned commitment or empty-hand Pass for every configured hero, joint reveal, Initiative and tied-Initiative choice, Hold, printed Movement with cumulative waypoint routes and Stop, adjacent/Ranged Attack with one legal Defense discard or decline, immutable four-turn assignment history, and a resumable end-of-round cursor. On a configured map with one declared starting Battle Zone, Minion Battle compares current Red/Blue minion counts, completes ties without effect, auto-resolves a forced removal set, or pauses on a round-owned typed losing-team choice. That choice carries stable resolution/choice/team/Battle-Zone identities, required count, intrinsic typed candidates, one-at-a-time Heavy-last legal select/deselect sets, current selection, and exact typed invocations. Confirmation removes the exact authoritative selection through ordered non-Heavy-before-Heavy events and advances the owning stage once. Losing the last minion records a typed end-of-round Lane-Push request that remains pending through token/marker cleanup and stops the advance at its consumption stage; that stop rejects with `UnimplementedLanePushConsumption`, which says the rule is unwritten rather than blaming an absent handler, and leaves both the cursor and the request in place for the milestone that will consume them. Eligible cards return to canonical owners; equal-count configured fixtures still complete two uninterrupted synthetic rounds and reuse in the saved validation scene.

Schema-versioned snapshots cover participants, selected map ID/revision, board occupancy, card facets, Initiative/Tie Breaker, current/completed assignments, end-of-round state, pending Movement, Attack/Defense, Skill, or displaced-minion-correction continuations, the complete pending hero-or-minion Minion-Battle selection, and an unconsumed end-of-round Lane-Push request. The current persisted snapshot schema is v12, which adds the repeated action instance a paused after-action correction still owes and explicitly rejects v11; routes for the retained after-action correction remain re-derived from the restored board, and the owed instance carries identity alone, rebinding its effect from the trusted definitions and being refused at load where they no longer supply it. The synthetic Hazard definition is at revision 3 because catalog content supplies its property declaration and that property's typed rule, and the capability registration list carries the five synthetic modification capabilities. A payload naming a superseded revision or a capability set this build does not register rejects rather than silently acquiring current semantics; no persisted state exists outside the test corpus. Component instance IDs are the deliberate exception: they are opaque wire data that nothing parses or re-derives, so a payload whose IDs were composed under an earlier shape still restores and still names the same components, and a change to their composition is accepted without migration. The eight representative fixtures are pinned at v12 and round-trip byte-identically, and the aggregate-invariance equality groups remain unchanged. Director Undo retains immutable initial scenario inputs plus accepted typed commands, rebuilds fresh authority, replays the retained prefix through the same typed `Execute` path, and verifies byte-identical state/events across two rebuilds. Private replay candidates retain atomic rollback checks but defer unobserved intermediate immutable projection construction; the adopted live session still publishes the one final current projection. Snapshots remain the separate persistence/diagnostics/resynchronization boundary. The read-only HUD exposes Tie Breaker, Undo, Restart, and the rule-event log.

Every enum in the payload is decoded through `SnapshotEnumReader`, which reads the int32 and refuses any value that is not a declared member of that enum under the typed `SnapshotLoadRejectionReason.UnrecognizedEnumValue`, naming the field, the type, and the offending value. The boundary guarantees membership only: rejecting `None`, or a member illegal in a particular position, stays with the domain constructors that own those rules. Declared members are cached per enum type rather than resolved through `Enum.IsDefined`, because `MatchAggregate.Rollback` runs this decoder on every refused or faulted command. Code-truth check 6 in the living-document validator fails on any raw `(SomeEnum)reader.Read…` cast remaining under `Core/Snapshots/`, so the guarantee is uniform across readers rather than dependent on which constructor happens to validate.
