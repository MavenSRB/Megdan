## Current implementation

### Application, configured presentation, and governance

The project has completed roadmap milestones through **7.9a**. Earlier phases established the corrected and independently verified Phase 4 architecture/performance gate, deterministic command-replay Director Undo, the internal rule-event log, the reviewed `official-single-lane` revision 1 map and exact setup, map-bound snapshots, authoritative zone/Lane queries, the pure application port, distinct Movement/Attack-Defense/Fast-Travel/Clear handlers, cached feature projections, bounded diagnostics, and configured saved-scene MVP/input cutover. The configured scene has no legacy controller: its composition root creates the bounded session, peer presenters/passive views, authority-free HUD, and passive board callbacks.

One dispatcher owns live typed commands, replay, Undo/restart, restore, ordered events, and immutable projections, while five concrete backends own handler-specific pending state and mutation and are reached by direct composition rather than through a registry. Action-kind dispatch is that direct composition; capability dispatch alone is data-driven lookup through `EffectCapabilityCatalog`, because a capability reference arrives as data inside the definition the resolver is walking and cannot be named at compile time. The contextual End Turn control forwards only a projected stop - the Hold, the Movement Stop, or an effect choice's own - and is suppressed during every mandatory choice that projects none. Action offers carry a decided availability, asked of the code the matching start asks: a Skill whose feasibility walk proves its effect can apply nothing, an Attack whose target query finds nobody. Either is drawn greyed and still refused atomically at the start, and both answer true wherever they cannot be asked, so an action is refused for being proven empty and never for being unjudgeable. p.12 is the source - Hold exists so a player is never forced to act - and the turn stays spendable on the card's other actions, including the Clear replacing an unavailable Attack, which p.13 gives its own legality.

A Skill is an ordinary printed action offer resolved over an immutable, catalog-owned `EffectDefinition`: a flat table of stable nodes with `Sequence`, `Optional`, `Conditional`, `Choose` and `RepeatAction`, where `Mandatory`, `may`, `up to` and `if able` stay four distinct behaviors rather than one failure path. `PendingResolution` carries identity, a continuation stack, completed outcomes and accepted choices - references only, never an `EffectDefinition` object or a handler, so the snapshot written from it has nowhere to put semantics. Every decision inside an effect frame rides one `AnswerEffectChoice` command carrying the invocation the pending choice projected, including the token and marker decisions described below. Presentation forwards those invocations and nothing else; [CONFIGURED_PRESENTATION.md](CONFIGURED_PRESENTATION.md) owns what a paused frame renders and what it withholds. The Skill seams hold the same bar as Movement and Attack: a start revalidates the offer and invocation context, and the effect-answer path prechecks pending identity and source-card state, so a bad state rejects with a typed reason rather than faulting at completion. A Skill whose root completes during its own start resolves there and emits the ordinary started/node/completed stream. The chooser's own option filtering, and the pause a mandatory node whose every option is refused makes behind one projected stop, are stated once in [CARD_EFFECT_CAPABILITIES.md](../CARD_EFFECT_CAPABILITIES.md) with their surface in [CONFIGURED_PRESENTATION.md](CONFIGURED_PRESENTATION.md). The stop is derived rather than stored, so restore, replay and retained-prefix Undo re-derive it as the state then stands, and a stale or forged select naming a refused option is rejected atomically. A target selection's declaration of the node it selects for, which lets a step offer only the objects its consumer can act on, is maintained in [Card-System/RESOLUTION_AND_EFFECTS.md](../Card-System/RESOLUTION_AND_EFFECTS.md). Refusals report Skill-specific rejection reasons, Skill facts materialize under their own `SkillActionProgressed` turn event kind, a paused Skill frame suppresses projected Fast-Travel options as paused Movement and Attack do, and restore re-derives a paused capability's candidates from the persisted completed outcomes through the resolver's own binding path. A definition can also ask for its own action to happen again through a `RepeatAction` node, bounded at two instances by construction because the second runs under a repeated context in which the node is ineligible; that node, the dispatcher's handling of it and the one paused state it crosses the wire in are maintained in [Card-System/RESOLUTION_AND_EFFECTS.md](../Card-System/RESOLUTION_AND_EFFECTS.md), which took this account at 7.1's threshold ownership review.

Board occupancy has one seam: an internal per-space index owns the one-obstacle-per-space rule for heroes, generic obstacles, minions, and tokens through a single collision-checked add, so a new occupant kind joins by declaring a typed occupant rather than a parallel mechanism, and per-kind identity validation stays with each kind. Reachability consumes that index through an authority-backed query entry. Timing checkpoints are resolver-emitted: a card action returns one ordered step stream interleaving its rule facts with the checkpoints it raises, and the turn authority materializes that stream without reading any fact's kind. The cross-platform dotnet harness compiles Core, Application, and the Unity-free Edit Mode tests unmodified, with a Unity-dependent exclude list acting as a build tripwire and a map-loader shim guarded by a parity fixture; scope and commands live in `Docs/AI/Testing/DOTNET_HARNESS.md`.

Per-milestone outcome, validation, and review evidence lives once in each commit body, addressed by SHA from the [Phase 6 archive](../Archive/Phase-Handoffs/PHASE_6.md).

### Movement and action architecture

The Phase 4 gate is closed; its record is indexed from the [Phase 4 archive](../Archive/Phase-Handoffs/PHASE_4.md). Segmented typed Movement continuation runs on the exact selected map: shortest and deliberately longer cumulative waypoint routes to the same destination commit their selected ordered adjacent steps through the configured match session, a typed evaluator applies prevention or a distance limit once at Movement-action start, and the effective allowance is captured in existing pending state for continuation, restore, replay, and Undo boundaries.

Fast Travel is a distinct typed replacement action on the match-session command path. It accepts empty destinations in the actor's current zone or a shared-border adjacent zone, requires no empty-space path, rejects non-adjacent zones and enemy hero/minion presence in either endpoint zone atomically, records ordered replacement/relocation/completion facts, resolves the played card, and suppresses source-card text even when replacing Primary Movement. The application projection exposes only currently eligible Fast Travel replacements and their authoritative legal destinations. The configured passive HUD shows an eligible replacement as a `FAST TRAVEL` button, leaving normal actions and an unhighlighted board as the default; only explicit button selection exposes that exact destination set. A highlighted coordinate then submits the existing typed `PerformFastTravel` command through `BoardInteractionPresenter` and `IMatchSession`; presentation performs no zone, enemy-presence, or destination-legality calculation. Replay and Undo use the same command path.

The registered backend split is sound for the implemented families. Movement and Attack/Defense retain their serializable pending continuations; Fast Travel and Clear are immediate replacement backends, while Skill owns the catalog-bound effect frame and its serializable pending continuation. Clear deliberately uses the existing direct replacement seam rather than implementing the still-deferred generic `ReplaceAction` effect node. The outer application/round/turn dispatch continues to enumerate authority-level command families, while choices inside an effect definition use the shared `AnswerEffectChoice` command.

### Match state, replay, and configured scope

Authoritative pure C# state currently covers map-scoped identity, the immutable selected map revision, participant `PlayerId`/`HeroId` relationships, initial Tie Breaker, synthetic hands whose size is fixture composition rather than a modelled rule - the default configuration and the configured scene both deal p.15's five over p.6's remaining thirteen, while the Skill fixture deals eight - owned commitment or empty-hand Pass for every configured hero, joint reveal, Initiative and tied-Initiative choice, Hold, printed Movement with cumulative waypoint routes and Stop, adjacent/Ranged Attack with one legal Defense discard or decline, immutable four-turn assignment history, and a resumable end-of-round cursor. On a configured map with a current Battle Zone, Minion Battle compares current Red/Blue minion counts, completes ties without effect, auto-resolves a forced removal set, or pauses on a round-owned typed losing-team choice whose shape and confirmation are maintained in [Card-System/TIMING_AND_TRANSITIONS.md](../Card-System/TIMING_AND_TRANSITIONS.md). Losing the last minion records rulebook p.8's end-of-round Lane-Push cause; what that request and its mid-turn sibling carry, and where each of them stops, lives in [BOARD_OPERATIONS.md](BOARD_OPERATIONS.md). The cursor runs all six of p.8's ordered steps and declares none of them unavailable: a round with nothing to push completes that step having pushed nothing, and a push that ends the game reports the step it ended at. Eligible cards return to canonical owners, and the current-round event projection empties when the next round opens, while the whole-match log and the completed-round record keep what it held.

The registered operations that change the board - tokens and markers with their derived supplies, direct Move and Object Push, Clear, and Place beside Spawn - are maintained in [BOARD_OPERATIONS.md](BOARD_OPERATIONS.md). The seam itself stays here: each of them asks the board for a validated relocation, placement, or removal through a named port rather than reaching the authority, none of them is a Movement action, and every decision inside one rides the existing `AnswerEffectChoice` command rather than a pending-choice class of its own.
Modifiers, restrictions, permissions, immunity, `Counts As`, the three-way obstacle classification they qualify, and the per-activation identity every effect source mints are maintained in [RULE_MODIFICATIONS.md](RULE_MODIFICATIONS.md). The contract boundary itself stays here: a rule is definition content on a trusted catalog rather than snapshot state, the live set is derived per command from active sources, and every rules-consuming seam takes it as a required parameter.

Schema-versioned snapshots cover participants, selected map ID/revision, board occupancy, card facets, Initiative/Tie Breaker, current/completed assignments, end-of-round state, pending Movement, Attack/Defense, Skill, or displaced-minion-correction continuations, the complete pending hero-or-minion Minion-Battle selection, and unconsumed end-of-round and mid-turn Lane-Push requests. The current persisted snapshot schema is v21, which adds the record of which heroes bought a level in the current round to the round section. Every superseded version, v20 included, was rejected on its own equivalent ground, recorded at the constant itself and in the corpus fixture rather than restated here. The retained after-action correction re-derives its routes from the restored board; the owed repeated instance carries identity alone and rebinds its effect from the trusted definitions; and the mid-turn Lane-Push request carries its cause, because a restored board cannot tell a side emptied by a Defeat or a Remove from one emptied by a move p.8 excludes. The registered component and capability sets ride the payload too, so a build whose content differs is refused rather than reinterpreted. A payload naming a superseded revision or a capability set this build does not register rejects rather than silently acquiring current semantics; no persisted state exists outside the test corpus. Component instance IDs are the deliberate exception: nothing parses or re-derives them, so a change to their composition needs no migration. The eight representative fixtures are pinned at v21 and round-trip byte-identically, with the aggregate-invariance equality groups unchanged. Director Undo retains immutable initial scenario inputs plus accepted typed commands, rebuilds fresh authority, replays the retained prefix through the same typed `Execute` path, and verifies byte-identical state/events across two rebuilds. Snapshots remain the separate persistence/diagnostics/resynchronization boundary.

Every enum in the payload is decoded through `SnapshotEnumReader`, which reads the int32 and refuses any value that is not a declared member of that enum under the typed `SnapshotLoadRejectionReason.UnrecognizedEnumValue`, naming the field, the type, and the offending value. The boundary guarantees membership only: rejecting `None`, or a member illegal in a particular position, stays with the domain constructors that own those rules. Declared members are cached per enum type rather than resolved through `Enum.IsDefined`, because `MatchAggregate.Rollback` runs this decoder on every refused or faulted command. Code-truth check 6 in the living-document validator fails on any raw `(SomeEnum)reader.Read…` cast remaining under `Core/Snapshots/`, so the guarantee is uniform across readers rather than dependent on which constructor happens to validate.
