## The panel and its regions

Milestone 7.8a rehouses every surface above on one runtime UI Toolkit panel, by the recorded user decision, and the retained visual tree replaces the immediate-mode drawing the HUD used from milestone 4.4c to here. `ConfiguredMatchHudRenderer` still owns the drawing surface and still holds no session; it creates the panel and its layout in code rather than from assets, lays out five absolutely-placed regions from pure functions of the viewport, and answers where the pointer is blocked from the live element bounds with those same rects as the fallback.

The settings object is the one exception, and milestone 7.9 made it one. Unity's text shaper needs ICU data, and the player only ships that data when the **build contains at least one `PanelSettings` asset** - the player says exactly that in its own log. A HUD that built its settings entirely with `ScriptableObject.CreateInstance` gave the build no such asset, so the data was absent and every label the HUD redrew raised a `NullReferenceException` out of `UITKTextHandle.ShapeText`. The Editor never showed it, because the Editor has the data loaded either way.

`Assets/Resources/UI/GuardsRuntimePanelSettings.asset` is therefore committed, and the panel is copied from it with `Instantiate` when it loads, falling back to a bare instance when it does not. Two things are worth knowing before anyone edits it. The asset's own `m_ICUDataAsset` field is empty on disk and stays empty - it is not what carries the data; its presence in the build is. And it is instantiated rather than used directly, so the per-panel values set beside it stay runtime state and never dirty a tracked asset. The layout is still code-owned, which is what the paragraph above is about. The player-build smoke gate is what found this, and only because milestone 7.9 made its smoke path play whole rounds instead of accepting one command - one redraw never reached the shaper. Every presenter, view model, typed invocation, and passive-view interface is unchanged: the migration stops at the `I*View` seam, which is why it changed no rule, no command, and no legality.

The standing HUD is the approved [milestone 7.8a mockup](../References/MILESTONE_7_8A_UI_MOCKUP.html). One status strip carries round and turn, both teams' Life counters, the Wave counter, and the Tie Breaker, which is relocated into it rather than dropped - the same counters and revealed side that the retired top-right box guaranteed, with the whole of it still available as one line for the chip's assistive reading. Two compact rails sit on the screen edges, one per projected hero and repeated rather than a pair of singletons: a team-coloured disc bearing the hero's initial from an optional configured icon field, the projected display name and Level, p.16's item bonuses as compact channel-abbreviation chips carrying a signed value, four fixed slots taking each played card's authoritative colour with the turn ordinal and colour only in the hover and assistive label, and a fifth distinct slot showing the discard pile's projected count beside one pip per colour in it. Both rails together take less than half the width, so the board stays the dominant surface. A small `DIRECTOR` toggle opens a compact drawer holding `UNDO`, `RESET` - presentation terminology for the existing Restart - and `EVENT LOG`; opening or closing it submits nothing.

## The card tray

The card tray shows one hero's whole current round, colour-coded from each card's own projected `CardColor` and never from team, hero, hand position, display name, art, or action type, with the colour's name on the button beside it. It sorts already played cards in ascending turn order, then the ones still available, then the discarded ones; a played card reads `PLAYED · TURN <n>` and never names a round, an available card sits visibly higher through a margin that changes no hit target or keyboard order, and the three groups are read from projected card lifecycle plus the round's own assignment history rather than from movement the presenter watched. Which hero it shows is local state with no control of its own outside the map: it follows the hero the match is waiting on, and a map click pins another until the awaited hero changes. A hero click is offered to the authority first, so a legal Attack target stays a spatial decision, and only a click the authority has no use for becomes a view selection.

## The one contextual region

One contextual region above the tray presents whatever the match is currently asking, and the tray is hidden rather than merely inert while a mandatory decision stands, so exactly one interaction context is usable. That region now also draws the paused multi-step system transition no view drew before - a gap open since milestone 6.11 built rulebook p.8's Lane-Push respawn pause, and made ordinary by milestone 7.6, because p.8's Pity Coin leaves a hero able to afford a level and p.15's Upgrade a Card then stops the end of round on a real choice from the second round onward. The options and their meanings are projected: the rules that paused describe their own pause as typed facts - hero, level, paid cost, remaining coins, and per option the card returned to the deck, the card taken, the sibling set aside and the printed icon whose dashboard slot makes it an item, or the destination space p.8's sidebar Place offers - and presentation composes the words from those facts without ever decoding an option identity. Answering forwards the invocation the continuation itself projected; an option this prompt did not project is refused before it reaches the authority. No End Turn and no end-of-round advance is drawn beside a pause, because the authority projects no stop and would refuse the advance. The scene runtime's milestone 7.6 command surface is retained explicitly as the director and headless path, for the build-smoke driver and every fixture that reaches a pause without a pointer.
