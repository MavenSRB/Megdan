### [x] 8.35k Give a relaunched player a road back to their own reserved seat

User-approved corrective of 2026-09-03, reported from the live playtest verbatim: "rejoin does not work, if user disconnects, its seat stays away, and connection is refused." Milestone 8.34 built the whole return mechanism - a reserved seat, a host-minted capability, a reclaim message, a rotated epoch - and it works. What it never had was a road to it. The capability lived in one private field of one live `PrivateSessionClient`, and three ordinary player actions end that object: the process exiting, the process crashing, and pressing LEAVE. After any of them the lobby could offer only a FIRST join, which the host refuses by name because the seat is reserved. Every reconnect fixture at every tier - the six-client rehearsal included - replaced only a socket beneath a surviving client, which is the one path a real player never walks.

Observable outcome: A player whose game died relaunches it, enters the same invitation, and is returned to their own seat with a rotated epoch and a complete projection. A player who deliberately leaves gives that seat up instead. And the host can hand a reserved seat back by a deliberate act, for the evening where a player's machine is gone and no stored capability can exist.

Acceptance checks:

- A brand-new client object for a seat the host holds reserved is returned to it by reclaim, with the epoch rotated and the authoritative version unmoved while the seat was away. The fixture constructs a second, distinct client and copies nothing out of the first, because reusing the object is what every existing reconnect fixture does and is exactly the path that was never broken.
- Leaving forfeits and crashing does not, asserted as one case in both directions: a deliberate Goodbye returns the seat to Open where an ordinary keyed claim takes it, while a dropped link leaves it Reserved and refuses the same claim by name. A build that forfeited every departure and a build that reserved every departure each pass one half alone.
- The retained capability answers for one session correlation and one seat only, so it can be replayed into neither another session nor another seat.
- The host's release control hands back a reserved seat and refuses a claimed one: a live player is never displaced by it, it is never automatic, and it is never on a timer - the reservation's absence of any clock is a feature, and an auto-release would give a dropped player's seat to whoever reconnected first.
- The session key stays an invitation and never an authorization: a client with no retained capability is refused a reserved seat although it holds the key every invited player holds. `HandleReclaim`'s checks, its identical answer to both wrong-capability cases, and the epoch rotation are unchanged.
- The capability is owner-private and stays out of every roster, projection, log line and diagnostic marker; the rehearsal runner greps every returned log for the shape a leak would take, beside the session key it already refused.
- The host log tells the two departures apart, and a refused client records `LOBBY_REFUSED reason=` - the diagnostic gap that left the failed playtest's refusal shown on one screen and written down nowhere.
- No wire, protocol, schema or content change: the protocol stays `guards-private-online/4` and the schema v35. `ReclaimSeat` and the capability mint already existed and are untouched; a released seat reaches every client as the roster's existing `Open` occupancy.
- The six-client rehearsal gains a third cohort whose cut ends a PROCESS rather than a socket, and whose relaunched process must return by `SEAT_RECLAIMED` with a rotated epoch and converge on the same outcome as the other five.

Closing check: `FreshProcessRejoinTests.ABrandNewClientForAReservedSeat_ReclaimsIt_WithARotatedEpoch`, `LeavingForfeitsTheSeat_WhileACrashKeepsItReservedForItsPlayer`, `TheHostCanReleaseAReservedSeatByHand_ButNeverALiveOne`, `ARetainedCapability_AnswersForItsOwnSessionAndSeatOnly` and `TheSessionsEventKinds_AreDistinct_SoAReleaseIsNeverReadAsAMatchStarting`, with `PrivateSessionSeatClaimTests.AGoodbyeFromASeatedConnection_ReleasesItsSeat` and `AReleasedSeat_TakesAnOrdinaryClaim_WhereAReservedOneRefusesIt`, are each recorded failing with the fix disabled at its own site and passing with it restored.

Non-goals: No expiry, timer or automatic release of a reservation; no change to how a capability is minted or checked; no wire, protocol, schema or rules change; no production presentation of the lobby; no reconnect behaviour beyond returning a player to a seat the host is already holding for them.

The failure is terminal for the whole table rather than a dropped frame: `SendProjectionTo` has already advanced the send sequence when the throw lands, so every client reads a Gap, the resync it asks for is served down the same throwing path, and the exception unwinds `PublishProjections` so no later connection is served either. The match stalls for all six players with nothing on any screen and no recovery.

Observable outcome: a match that runs to its own ending, past forty completed rounds, keeps every seat projection frame inside the protocol's payload bound, and a seat that disconnects and returns mid-match is served the same bounded window as one that never left. Each seat reviews the four most recent completed rounds; the rules, the restore state and the authoritative snapshot still hold every round the match played.

Design:

- The bound is `MatchSessionProjection.RetainedCompletedRounds`, applied at the READ MODEL rather than in the codec, so `MatchSessionProjection`, the `SeatProjection` derived from it and the `NetworkMatchClient` that decodes it all report the same window. A cap inside `WriteCompletedRounds` would have made the encoded frame disagree with the projection it was encoded from, which is the one thing convergence is asserted on.
- `MaxPayloadBytes` is deliberately NOT raised. Its own doc comment states its purpose - a declared length cannot buy an allocation - so it is a defensive read-side cap applying to every message kind from every peer; raising it would weaken that for all of them and leave the term unbounded, producing the same freeze at a higher round number. A growth term with no limit is not fixed by a larger limit.
- `RoundResolutionAuthority` is deliberately not windowed, and now says so at its own `CompletedRounds`. This is a bound on what a seat is SHOWN, not a loss of history.
- Four is measured rather than chosen: the frame decomposes into 35,997 bytes that do not grow with match length plus 1,108 bytes per retained round, so a window of four saturates it at 40,431 bytes - 61.7% of the 65,536-byte ceiling and 77.2% of the frame fixture's deliberate-resize guard, leaving 11,964 bytes against the 2,835 bytes the rest of the frame grew across all of 8.33 to 8.35r. Four is also the measured reach of the 8.35r match-log window this same projection already carries, so the two history surfaces a seat reviews cover the same span rather than one of them silently deciding what recent means for both.
- No wire version and no schema move: `PrivateSessionProtocol.cs` and `Core/Snapshots/` are absent from the diff, the field is already a count followed by that many records, and the snapshot captures the authority's own full list.

Acceptance checks:

- `PrivateOnlineEventChannelTests.TheProjectionFrame_StaysInsideItsBound_ThroughAMatchThatRunsToItsOwnEnding` drives until the match ends itself and refuses to pass unless it saw an ending past forty completed rounds, building the frame through the real codec so an over-long frame fails as the host's own exception rather than as a number. The pre-existing guard measured 700 wire steps, about eight completed rounds, which is why a 33-round failure shipped past it.
- `TheReadModelsRoundHistory_IsTheRecentWindow_WhileTheMatchKeepsEveryRound` asserts both halves at once: the host's read model and all six seat views hold exactly the last four rounds, while the authoritative snapshot still restores every round played. Without the second half this would be a fixture that passes while history is destroyed.
- `AReturningSeat_IsServedTheRetainedRoundWindow_OverTheWire` puts the resync path under the window on a wire walk that has already outrun it, holding `AssertConverged` byte for byte.
- Pre-fix red: the behavioural line in `MatchSessionProjection`'s constructor reverted with the new constant left declared and inert, per this repo's own ceremony rule for a check that needs new typed vocabulary to compile. Both new cases fail at that revision, the frame case with the same exception at the same site and with the same message as the live host crash.
- `EndOfRoundContinuationTests` and `CompleteCoreMatchLoopTests` were made window-aware deliberately rather than relaxed: the advance-count claim and the round-boundary edge detector now derive from `RoundIndex`, because a windowed count saturates and would have silently weakened "every round crosses six stages" to the last four.

Non-goals: no protocol, wire-version or schema change; no bound on the round authority, the restore state or the authoritative snapshot; no change to what a seat is authorized to see.

### [x] 8.35y Make the board's events visible with kinetic cues

SIXTEENTH amendment, from the user's own playtest reading: "the biggest issue in playtest was that players were not aware whats happening. Can we do some cutscene for attacks or something? Tokens smacking each other?" A primitive-idiom kinetic pass - no production art, no camera seizure, no gated input, and nothing a player has to wait for.

Observable outcome: a piece that moves travels from the space it left to the space it reached instead of teleporting; an attacker leans into the HERO it struck and carries a floating damage figure; a struck piece registers the hit, and a blocking defender flashes with its own block figure; a removed piece fades for as long as it is still drawn; a returning piece pops in. Standing and separate in kind: the acting-hero ring breathes while the viewer is being waited on, and an awaited hero's gold tray and card shine carries a slow circling light.

Design:

- Every cue derives from milestone 8.35r's `MatchLog` and nothing else. That log admits only events the whole table can already see - its seat filter is an identity rather than a redaction - so a pure function of it plays the same story on every client with nothing sent between them, and a cue can never reveal what the log's own selection contract excluded. `IMatchReadModel` exposes no diagnostic stream, so this is also the only event source Presentation has.
- Three rules make a kinetic layer safe on an authoritative surface. A cue is emitted ONCE, keyed on its log row's own `Sequence`, so a resync redelivering a window cannot replay it. The FIRST projection a client sees primes the watermark and plays nothing, so joining a match in progress does not fire forty smacks at once. A log that went BACKWARDS - undo, rewind, restore - re-primes, plays nothing and clears the floating figures, because a figure describing an event that no longer happened is the one thing a flourish must never do.
- End states are projection-true structurally rather than by testing for it: the view recomputes each piece's AUTHORITATIVE placement every frame from its own projected occupancy - the same arithmetic the board views already use - and then ADDS the kinetic offset. It never integrates and never moves a piece relative to where it currently is, so an interrupted cue, a mid-slide projection change, an undo, a resync and a restore all resolve to authoritative placement on the next frame with no unwind step.
- Two findings contradicted the amendment's assumptions and are recorded rather than improvised around. The events do NOT carry movement steps - `MatchLogEntry` names a per-hex step as one of its own exclusions and the log keeps only the first origin and last destination - so a slide travels TWO waypoints; `KineticCue.Route` is shaped for N and the view interpolates an arbitrary polyline, so a later milestone that carries the real route drops it in with no view change. And the attack rows carry no damage amount, so the figure is the PRINTED value on the card the log named, read from the definition catalog, with its colour taken from that card's own `CardProgressionProfile` through `MatchHudTheme.Face` - the same source the user pinned for colour, never a presentation-side palette guess.
- Failure is bounded by construction: `KineticCueDriver` catches its tick, reports it, and disables itself after three failures, leaving exactly the projection-change redraw the board did before this milestone; the coordinator refreshes `kinetics` last and isolated under 8.35h's per-panel isolation; every seam is optional and appended, so every existing composition and fixture keeps its exact call.
- Nothing animates that is not awaited: board marks pulse only while the viewer is being waited on, and the shine sweeps only for heroes the awaited predicate names. Standing animations are periodic functions of accumulated time - one multiply per element per frame, no per-element state, nothing allocated while they run - and cues are capped at six concurrent, a burst keeping only the newest.

Acceptance checks:

- `KineticCueTests` and `KineticPlaybackTests`: derivation from the log, the once-only watermark, the priming projection, the backwards-log re-prime, the printed figure and its printed colour, and the whole timing vocabulary asserted against the amendment's own 200-400 ms band so a kind added later cannot sit outside it.
- `KineticCuePlayModeTests.TheRealHud_SlidesThePieceItMovedAndLungesTheAttackItResolved` proves it on the shipped surface, through the real controls across two rounds: the configured scene composes a kinetic view and attaches the driver, a real movement puts the piece on the two recorded waypoints, ONE ORDINARY FRAME advances that slide with nothing in the case ticking it - which is the whole of what plays on the real HUD means - and the piece resolves to the placement the projection alone decides; then a real attack on the now-adjacent enemy hero leaves the attacker lunging at it and at no other piece, and the lunge ends inside the vocabulary own longest bound.

Named gaps, all recorded rather than worked around:

- **An attack on a MINION plays no lunge and no flash**, which is the commonest attack in a match and the one the amendment named. The cause is upstream of this pass and was found by its own Play Mode case: `CardActionResolutionEvent.FromAttackResolution` builds every attack-resolution event with the actor and `TargetHeroId` but leaves `targetMinionId` at its default, so the row reaches the seat-public log with an attacker and no defender, and the presenter correctly declines to invent one. The repair is one line - `targetMinionId: resolution.TargetMinionId` - and the receiving code is already in place: `RuleEventLogProjection` writes `minion=` for any defined value, and `MatchLogEntry.SubjectMinionId` is documented as exactly a target, a defeat, a Minion Battle removal. It is NOT made here because it is a Core change whose effect reaches the rule-event log inside the snapshot envelope digest: measured at this revision it moves the compatibility corpus, so it owes an explicit migrate-or-reject decision and a re-pin, which is a milestone of its own rather than an integration-time edit.
- **A defeated piece is not HELD on screen while it fades**, so in practice a removal still reads as a disappearance. The hold was implemented by re-activating a `GameObject` the board view had already deactivated, which is the one place this layer would show a piece the projection does not contain, and it did so behind the owning view's back on an object that view pools and reuses. The complete unfiltered Play Mode run found the cost: five existing journeys assert that a defeated miniature has LEFT the board - rulebook p.13's removal, and a real acceptance check of the milestones that wrote them - and the hold made all five report the piece still present. Cut rather than traded for five weakened rules guards. Delivering it properly is a BOARD VIEW change, since that view owns the piece's lifetime and its pool and is the only thing that can honestly defer a removal until a cue has finished.
- The awaited hex-corner cues do not pulse yet; only the acting-hero ring does.
- The circling shine sweep is the least verified surface here and is cuttable in isolation.

Non-goals: no production art, no camera control, no input gating, no rules, wire or schema change, and no cue for anything a player has not yet committed to.
