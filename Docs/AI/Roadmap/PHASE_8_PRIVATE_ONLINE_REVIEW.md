### F-ONLINE-01 - Authenticate a deliberate leave

`PrivateSessionHost.OnFrame` (`Assets/GuardsDigital/Application/PrivateOnline/PrivateSessionHost.cs:612-642`) explicitly exempts plaintext `Goodbye` from keyed-channel verification. It calls `Depart(..., forfeited: true)`. `Depart` (2102-2124) opens the seat, clears its capability and resets its epoch. A socket disconnect instead reserves the seat. `PrivateSessionClient.SendGoodbye` (1385-1389) sends directly through the outbox, bypassing its existing sealing helper.

This is a deterministic source-level violation: an injected unsealed leave on an established keyed stream destroys the owner's reservation. An on-path party capable of TCP stream injection need not know the session key to cause the release; a subsequently admitted key-holder can ordinarily claim the now-open seat. The claim that this is equivalent to a connection reset ceased to be true when voluntary departure acquired forfeiture semantics. This does not establish that any playtester exploited it or that an arbitrary off-path sender can target a TCP connection.

Existing `AGoodbyeFromASeatedConnection_ReleasesItsSeat` tests voluntary release; `APlaintextGameplayFrameOnAKeyedSession_DisconnectsThatConnectionAlone` tests an injected command. Neither combines a keyed seat with an unsealed leave and preservation of its capability. Preserve normal intentional leave and unkeyed loopback behavior.

Smallest correction: use the authenticated path for client forfeiture on a keyed session and refuse an unsealed forfeiture without making the seat Open. Update the precise security contract and compatibility assessment. The named check must first fail on the reviewed source: establish a keyed seat, inject plaintext Goodbye, require a reserved/reclaimable seat and refusal of an ordinary replacement claim; prove the same capability can reconnect. Add companion authenticated-leave release and replay/tamper cases. Observe the named check passing after correction. No separate interpretive verification milestone is needed for this mechanical contract.

### F-ONLINE-02 - Bound socket writes and cancellation

`TcpSessionListener.Send` (`Assets/GuardsDigital/Network/TcpSessionTransport.cs:121-146`) calls synchronous `NetworkStream.Write` under `SendGate`; `CloseConnection` (270-285) needs that same lock before closing the socket. The client duplicates this shape (369-407). Neither side configures a send timeout. Host `PublishProjections` sends serially (PrivateSessionHost.cs:1903-1920); both `PrivateOnlineDrivers.Update` (324-343) and `PrivateLobbyViews.Update` (791-820) drive this executor on the presentation pump. The bot fleet forwards human sends to the same transport.

A connected peer that stops reading can fill its TCP send path, blocking publication, other seats, host UI and timeout sweeping. A second thread cannot promptly cancel that write through the current close path because it needs the held send lock. Ordinary low-bandwidth healthy play may never fill the buffer. No stall duration, leak, frame-rate regression or occurrence in the accepted internet run was measured here; this is a concrete growth/liveness risk, not a claimed reproduced outage.

Smallest correction: give outgoing delivery a bounded, cancellable transport policy while preserving one serialized game authority, frame ordering and the reserved-seat pause. The named socket check must hold a seated peer connected but non-reading, force backpressure, and prove host pump/control service and disposal return within a declared test deadline (proposed maximum five seconds); a healthy observer still receives transport/status service, and the failed seat becomes Reserved without unauthorized gameplay progress. Observe failure before and pass after. A test that sends only one small frame without establishing backpressure is vacuous. Extend to the client close path and directly affected reconnect tests.

### F-ONLINE-03 - Apply resource limits below the protocol pump

The TCP accept loop creates a connection and receive thread before the host sees `Connected` (TcpSessionTransport.cs:197-224). Receive loops allocate bounded individual frames but enqueue them into an unbounded `ConcurrentQueue` (94, 251-255; client 317, 436-440). The host's twelve-connection check and five-second handshake sweep operate later in the consumer. Both production pumps drain until empty before sweeping. The listener backlog of eight limits pending accepts, not all accepted sockets/threads; the 64 KiB payload bound is not an aggregate memory bound.

Bursty or hostile pre-admission traffic can grow queued bytes/threads or monopolize the pump without ever acquiring a seat. This is reachable at the operator-exposed port, but no exhaustion was reproduced. The existing `ConnectionsPastTheBound_AreRefusedAtAccept` drives the application host, so it does not prove the adapter has bounded allocation before host admission.

Smallest correction: bound adapter connection allocation and queued bytes/events, with explicit overflow disposal and a finite drain budget that leaves time for sweeping. Keep rejection privacy and deterministic executor ordering. The named check must pause the consumer, exceed the declared adapter cap with connections and complete bounded frames, then assert threads/connections and retained bytes remain below published limits; on resume, healthy service and deadlines must progress and resources return to baseline after disposal. Record pre-fix failure and post-fix pass. Combine with F-ONLINE-02 under one transport outcome instead of creating per-file milestones.
