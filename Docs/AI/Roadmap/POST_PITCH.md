## Post-pitch production direction - not scheduled

- Formalize licensed product scope and name.
- Productionize the private-playtest networking architecture for the licensed product's availability, scale, security, privacy, and support requirements.
- Reassess listen-host, relay, dedicated-server, and migration requirements from measured playtest evidence.
- Productionize reconnect and lobby behavior; add matchmaking, accounts, and team communication if authorized.
- Add heroes **in batches of about five, not one at a time** (user decision, 2026-08-25, from milestones 8.20-8.22's measured cost). Every batch still starts with the same verified effect-family delta audit against the capability catalog before implementation is scheduled - what changes is that the audit, the vocabulary it names, the schema move, the showcase reachability content and the defect-finding pass are each done **once per batch** instead of once per hero. Three facts drive it. The audit already works: [Rules/ROSTER_CAPABILITY_MATRIX.md](../Rules/ROSTER_CAPABILITY_MATRIX.md) predicted four of Sabina's six vocabulary pieces by name and parameter a milestone before she was composed. What forces the per-hero repetition is `ConfiguredCardMatrixTests`' rule that every registered capability must already be reachable from a printed card, so a predicted contract cannot be registered until some hero's content reaches it - which is why 8.20, 8.21 and 8.22 each cost a schema version for the registration list alone. And latent defects surface per *combination* rather than per hero: 8.22 found three in shipped code because Sabina was the first content to make an effect frame publish all three of its completion results at once, so a batch that reaches more of the combination space finds them in one pass.
- A batch intake owes two changes before it is scheduled, both of which are why this is not worth doing for a batch of one or two. **Build the batch's whole predicted vocabulary as a lettered series and then register all of it in one milestone.** The reachability rule stays - dead vocabulary nothing exercises is exactly what it exists to prevent - and it is cheaper than it looks, because it has two halves: a *capability* need only be named by some card this build can deal, which includes each verified hero's own set, while only a new *handler implementation* must additionally be reachable from a showcase card. Showcase content is therefore owed per new handler, not per contract; milestone 8.22's five handlers cost two showcase hands and one continuation shape. No block need be larger than 8.19b, which built the whole reusable query/value/state vocabulary and moved no schema field: building is schema-neutral and only registering costs a version, so a series of ordinary-sized blocks followed by one registration milestone buys one schema move and one corpus re-pin for five heroes instead of five. What 8.19b itself missed is exactly that last step - it left its contracts in bounded test catalogs with no showcase hand reaching them, which is why 8.20, 8.21 and 8.22 each had to register their own subset and each cost a version for it. And **make the permanent player-path gate's journeys declarative** - generated from the gate table as data rather than hand-written per hero - because the table plus roughly fifteen real-input journeys is the largest constant per-hero cost and the only remaining term that does not decay. Per-hero vocabulary cost already is decaying in depth if not in count: Arien's seven pieces included a new card-text altitude and the persisted field that caused schema v28, while Sabina's six were one predicate and five optional parameters and enum members whose defaults preserve existing behaviour, and none of them moved the schema.
- Validate additional platforms as separately approved tracks in the canonical order [Project/PRODUCT.md](../Project/PRODUCT.md) declares (user decision, 2026-08-14): macOS, then touch devices including the declared iOS target; Linux and closed platforms remain unscheduled until separately approved.
